# Writing style

The reader is an experienced Ember engineer with an hour to spare. The prose should read like a sharp colleague explaining something at a whiteboard: clear, connected and unhurried, never padded.

## Structure

- **One arc per concept.** What you know from Ember → what React does instead → why → the catch. Not every concept needs all four, but keep them in this order.
- **Lead with the point.** A paragraph's first sentence says what the paragraph is about. Supporting detail follows.
- **One idea per paragraph.** When a paragraph turns to a new idea, start a new one.

## Sentences

- **Show the logic.** Join related sentences with *because*, *so*, *whereas*, *which means*, *but* and *instead*. The reasoning is the lesson, so don't make the reader reconstruct it.
- **Vary the length.** Merge short sentences that make one point. Keep a short sentence when it carries the emphasis.
- **Name things once, then refer back.** "The dependency array … It …" reads better than repeating the term.
- **Use asides sparingly.** A parenthetical that runs over a few words usually belongs in its own sentence or in the code sample.

## Self-check answers

Learners say these out loud, so they should sound spoken: a direct first sentence that answers the question, then the reasoning. Write "first, second, third" rather than "1) 2) 3)".

## Budget

A rewrite stays within about ±10% of the original length. Polish means better connections, not more words: no warm-ups, recaps or hedging.

## Leave alone

- Exercise criteria are checklists, so keep them terse.
- Code samples and comments only change for accuracy.
- Flags (🟢 🟡 🔴), headings and terminology stay consistent across days.
