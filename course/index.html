Week 1 · Core mental model · Day 1

JSX, components, rendering

There is no autotracking. A component is a function that React calls again whenever anything upstream might have changed.

  1. 15 minConcepts
  2. 35 minHands-on
  3. 10 minCheck yourself

Concepts

Components are functions, re-run on every render

🔴 New mental model

Glimmer autotracks: reading a @tracked field during render registers a dependency, and only the parts that read it update. React tracks nothing. When state changes, React calls your component function again, top to bottom. It also calls every child it renders, unless they opt out. Then it diffs the new element tree against the previous one and commits the minimal DOM changes.

So UI = f(props, state). A render is a function call plus a diff, not DOM work. Expect your function to run many times, and keep it pure: no side effects, no mutation, same output for the same inputs.

A component re-renders when its state changes, its parent re-renders, or a context it reads changes. New props are not a separate trigger: they only arrive because the parent rendered.

JSX is JavaScript, not a template language

🟡 Same goal, different mechanics

JSX compiles to jsx(type, props) calls, so anything that works in an expression works in {}. Attributes are DOM properties, which is why you write className and htmlFor. There are no block helpers:

  • {{#if}} → cond && <X/>, a ternary, or an early return
  • {{#each}} → array.map(item => <Li key={item.id} …/>)
  • {{else}} → the other branch of the ternary
  • {{!-- --}} → {/* */}

You lose the compile-time knowledge Glimmer has about which parts are static. The React Compiler (Day 6) exists partly to win that back.

The 0 && trap

🔴 New mental model

a && b evaluates to a when a is falsy. React renders nothing for false, null and undefined, but it renders numbers, including 0. So {labels.length && <Labels/>} prints a literal 0 when the list is empty.

Always give && a boolean: labels.length > 0 &&, !!count &&, or use a ternary. Ember's {{#if}} treats 0 as falsy and renders nothing, which is why this one bites Ember developers in particular.

Plain functions replace helpers

🟢 Direct translation

There's no helper registry and no resolver. A helper is a function you import. Hoist expensive setup, like an Intl.DateTimeFormat, to module scope so it isn't rebuilt on every render.

Fragments

🟢 Direct translation

A component returns one node. To return siblings without a wrapper <div>, use <>…</>. When you need a key (in a list), write <Fragment key={id}>. Glimmer templates can have several top-level nodes, so you've never needed this.

Check yourself

Answer out loud first, then open the model answer.

1What triggers a re-render?

Three things: the component's own state changes (a useState/useReducer setter called with a new value), its parent re-renders, or a context it consumes changes. "Props changed" is not a separate trigger. Props only change because the parent rendered, and a child re-renders when its parent does whether or not its props changed, unless it's wrapped in memo.

2What is the difference between render and commit?

Render is React calling your components to get a new element tree and diffing it against the previous one. It's pure and has no DOM access. In concurrent mode it can be interrupted, restarted or thrown away. Commit is applying the diff to the DOM, then running layout effects, then (after paint) passive effects. Side effects belong in event handlers or effects, never in render, because a render may never be committed.

3Why className and not class?

JSX attributes map to DOM properties, not HTML attributes. The property is element.className, because class was a reserved word in early JS. Same for htmlFor (label.htmlFor). React 19 also accepts custom-element attributes as written, but for built-ins the property names stand.

4How do JSX and Glimmer templates differ in what the compiler knows?

Glimmer templates are a restricted language. At build time the compiler knows which parts are static and which are dynamic, and it emits opcodes that update only the dynamic bits, driven by autotracking. JSX is arbitrary JavaScript. To the compiler, jsx('div', props) is an opaque function call, so React has to re-run the component and diff at runtime. That gap is what the React Compiler closes: it analyses your components (assuming they follow the rules of React) and auto-memoizes values and JSX.

5What does {0 && <X/>} render?

The text "0". && returns its left operand when that operand is falsy, and React renders numbers (including 0 and NaN) but skips false, null, undefined and true. Fix it with a real boolean: {count > 0 && <X/>}.

Week 1 · Core mental model · Day 2

Props, children, composition, lists & keys

Args become props and blocks become children. Keys are where Ember instincts quietly fail.

  1. 15 minConcepts
  2. 35 minHands-on
  3. 10 minCheck yourself

Concepts

Args → props

🟢 Direct translation

Props are the one argument to your function. Destructure them in the signature and give defaults there. There's no this.args proxy and no @ sigil, and there's no difference between "args" and HTML attributes: everything is a prop. Spreading native attributes is {...rest} (Ember: ...attributes).

{{yield}} → children

🟢 Direct translation

Whatever you nest inside a component arrives as props.children, typed ReactNode. Render it wherever the yield would go.

Named blocks → ReactNode props

🟡 Same goal, different mechanics

There's no named-block syntax. A "slot" is just a prop whose value is JSX. That's more flexible than named blocks (you can compute it, pass it down, or default it), but (has-block "footer") becomes a plain truthiness check.

Block params → render props

🟡 Same goal, different mechanics

{{yield issue index}} hands data back to the caller's block. The React equivalent is a function prop that returns JSX: the child calls it with data, and the caller decides the markup. Since hooks arrived, render props are mostly used where the data comes from the child's render, like list items or virtualised rows. Hooks cover the reusable-logic case.

Keys are identity, not a performance hint

🔴 New mental model

React matches old and new children by type + key. If the key matches, the component instance is reused, along with its state, its refs and its DOM nodes. With key={index}, reordering a list keeps instance #0 at position 0 and gives it different data. Any local state (a typed input, an open dropdown, a focused element) now sits next to the wrong item.

Use a stable id from the data. And the flip side: changing a component's key on purpose is how you reset its state (unmount, then mount fresh).

Props are read-only; composition over configuration

🟡 Same goal, different mechanics

Never mutate props. In React 19 dev builds the props object is frozen, so attempting it throws. Data flows down, and changes flow up through callback props, which is DDAU, just enforced harder.

Prefer composition to configuration: rather than <Card showHeader headerTitle headerIcon …>, accept header={<CardHeader …/>} or children. This is also the first fix for prop drilling, before you reach for context.

Check yourself

Answer out loud first, then open the model answer.

1Why not use the array index as a key?

A key is how React decides which component instance (and its state and DOM) lines up with which item between renders. With index keys, inserting, removing or reordering items shifts the data under the existing instances. State, focus, uncontrolled input values and animations then stay at the old positions. Index keys are only safe for static lists that never reorder and whose items have no state.

2How do you reset a component's state?

Change its key. A different key means a different identity, so React unmounts the old instance and mounts a fresh one with initial state. <ProfileForm key={userId} /> is the idiomatic way to reset a form when the entity changes, and it's much better than an effect that resets each field.

3Render props vs children vs hooks: when would you use each?

Use children or ReactNode props when the parent just decides what goes in a slot. Use a render prop when the child owns data that the caller should turn into markup, such as list items, virtualised rows or a headless select's options. Use a hook when you want to reuse stateful logic with no markup opinion. Hooks replaced most render-prop and HOC uses for logic sharing; render props survive for per-item rendering.

4What is prop drilling, and what fixes it?

Passing a prop through intermediate components that don't use it, just to reach a deep child. In order of preference, the fixes are: composition (pass the deep child down as children or an element prop, so intermediate layers never see the data), then context for genuinely tree-wide values (theme, current user, a store), then an external store with selectors. Don't reach for context just to save typing.

Week 1 · Core mental model · Day 3

State: useState, immutability, derived state

Mutation is invisible to React. State is a snapshot, setters schedule a new render, and derived values belong in render.

  1. 15 minConcepts
  2. 35 minHands-on
  3. 10 minCheck yourself

Concepts

@tracked mutation → immutable replacement

🔴 New mental model

Autotracking notices this.issue.status = 'done' because the setter is instrumented. React doesn't instrument anything. It compares the new state with the old using Object.is, so a mutated object is the same reference, React sees no change, and nothing re-renders. Worse, other code holding that object now sees the change without having rendered it.

So you replace: new array, new object for the item that changed, and the same references for everything else (that's what lets memo skip work later).

State is a snapshot per render

🔴 New mental model

count is a const captured by the closure of this render. setCount(count + 1) doesn't change it. The setter schedules a re-render, and in that next render your function runs again and useState returns the new value. Logging right after the setter prints the old value. This is the single most common "React is broken" moment for people coming from mutable models.

Batching

🟡 Same goal, different mechanics

React batches every state update made in the same tick (event handlers, timeouts, promises) into one re-render. Ten setter calls produce one render. Ember coalesces through the runloop too, but there you can read the new value straight away. Here you can't (see the previous section). flushSync forces a synchronous commit, but you rarely need it.

Updater functions

🟢 Direct translation

When the next state depends on the previous one, pass a function: setCount(c => c + 1). React queues the updaters and runs them in order against the latest state, so calling it twice adds 2. With setCount(count + 1) called twice, both calls read the same snapshot, so you only add 1.

Derived state = compute during render

🟢 Direct translation

A filtered list, a count or a "Showing X of Y" are getters, not state. Compute them in the component body. Mirroring props or other state into useState + useEffect adds an extra render, a frame of stale UI, and a sync bug waiting to happen. Reach for useMemo only when the computation is measurably expensive.

Lazy initial state

🟡 Same goal, different mechanics

useState(expensive()) calls expensive() on every render and throws the result away after the first. Pass the function instead, useState(() => expensive()), and React calls it once, on mount. The initial… prop-naming convention (initialIssues) signals "read once, then owned locally".

Check yourself

Answer out loud first, then open the model answer.

1Why must React state be treated as immutable?

React detects changes by reference (Object.is). Mutating an object keeps the reference, so React bails out and the UI doesn't update. Immutability also makes renders consistent snapshots (needed for concurrent rendering, where a render can be paused or discarded), makes memo/useMemo comparisons cheap and correct, and lets features like transitions and undo keep older versions around.

2What does console.log(count) print right after setCount(count + 1)?

The old value. count is a constant captured by this render's closure. The setter only schedules a new render, and the new value appears when your component function runs again. To use the new value immediately, compute it into a local (const next = count + 1; setCount(next); use(next)).

3What is batching?

React groups all state updates triggered in the same tick into a single re-render and commit. Since React 18 this covers timeouts, promises and native handlers as well as React events. Multiple setters, one render. You can opt out with flushSync (rarely needed, for example before measuring the DOM).

4When should you use an updater function?

Whenever the next state is computed from the previous state: counters, toggles, appending to arrays, and especially when several updates might be queued in one tick or when the setter runs inside a stale closure (timers, subscriptions). set(prev => …) always operates on the latest queued value.

5Derived state vs useEffect + setState?

Derive it. An effect that sets state from props or other state causes a second render (the first one shows stale data), can drift out of sync, and is harder to follow. Compute in render, and add useMemo only if it's expensive. Effects are for syncing with external systems, not with other React state.

6How is this different from @tracked?

@tracked gives you fine-grained, mutable reactivity. You mutate a field, Glimmer knows exactly which template bits read it, and the new value is readable straight away. React state is coarse and immutable. You replace values, the whole component re-renders and diffs, and the new value is only visible in the next render's snapshot. Precision moves from the framework to you (memoization, state placement).

Week 1 · Core mental model · Day 4

Events & forms: controlled vs uncontrolled, refs

Two ways to own an input's value: React owns it, or the DOM does. Choose deliberately.

  1. 15 minConcepts
  2. 35 minHands-on
  3. 10 minCheck yourself

Concepts

{{on "click"}} → onClick

🟡 Same goal, different mechanics

Handlers are camelCase props taking a function. They're synthetic events: React attaches one listener per event type at the root container and dispatches through the React tree. The event object is a cross-browser wrapper (and has been unpooled since React 17). onChange on inputs fires on every keystroke, like the native input event, not on blur.

preventDefault and real forms

🟢 Direct translation

Same as in Ember: call event.preventDefault() in onSubmit to stop the full-page post. Prefer a real <form> with a submit button over a click handler on a div. You get Enter-to-submit, a11y and FormData for free. (Day 11: <form action={fn}> handles this for you.)

Controlled vs uncontrolled inputs

🟡 Same goal, different mechanics

Controlled: value={state} + onChange. React state is the single source of truth, re-rendering on every keystroke. Use it for live validation, character counters, dependent fields and formatting as you type.

Uncontrolled: defaultValue and let the DOM keep it. Read it on submit with new FormData(form) or through a ref. That's less code and fewer renders, and it suits simple forms and React 19 Actions.

Mixing them is a bug: value without onChange makes the input read-only, and switching between undefined and a string triggers the "changing an uncontrolled input to be controlled" warning.

useRef for DOM access

🟡 Same goal, different mechanics

useRef returns a mutable box { current } that survives renders and doesn't trigger a render when changed. Pass it as ref={inputRef} and React sets current to the DOM node after commit. Use it to focus, measure, scroll or reset an uncontrolled input. Don't read refs during render (they're unset on the first render, and they're outside React's data flow).

Ember: a modifier that receives the element. React 19 also has ref callbacks with cleanup, which are the closest thing to a modifier: ref={el => { setup(el); return () => teardown(); }}.

Labels and a11y

🟢 Direct translation

Wrap the control in a <label> or link them with htmlFor + id (use useId() for unique ids, never Math.random()). Testing Library's getByLabelText and screen readers depend on it. Errors go in an element with role="alert" so they're announced.

Check yourself

Answer out loud first, then open the model answer.

1Controlled vs uncontrolled inputs: trade-offs, and when to use each?

Controlled (value + onChange): React state always mirrors the input. That allows instant validation, derived UI, programmatic resets and input masking, at the cost of a render per keystroke and more code. Uncontrolled (defaultValue, read via FormData or a ref): the DOM owns the value. It's simpler, with fewer renders, and works with progressive enhancement and React 19 form Actions. Use controlled when other UI depends on the value as it changes. Otherwise uncontrolled is fine, and often preferable.

2What is a synthetic event?

React's cross-browser wrapper around a native event, with a consistent interface (target, currentTarget, preventDefault, stopPropagation). React delegates: one native listener per event type on the root container, dispatched through the React component tree, which is why events from portals bubble to their React parents. e.nativeEvent gives you the original.

3useRef vs useState?

Both persist across renders. Changing state schedules a re-render, and the value is a per-render snapshot. Changing a ref (ref.current = x) is a silent mutation: no render, and visible immediately. Use state for anything that affects output. Use refs for DOM nodes, timer ids, previous values and other instance-like data that render doesn't read.

4Why avoid reading the DOM (or refs) during render?

Render must be pure and may run without ever committing (Strict Mode, concurrent rendering, Suspense retries). On the first render the DOM doesn't exist yet, so ref.current is null. Later, the DOM reflects the previous commit, not the one you're computing. Read the DOM in effects, layout effects or event handlers, after commit.

Week 1 · Core mental model · Day 5

Effects: synchronising with external systems

useEffect is not didInsert. It keeps something outside React in sync with your props and state, and most code that reaches for it shouldn't.

  1. 15 minConcepts
  2. 35 minHands-on
  3. 10 minCheck yourself

Concepts

useEffect synchronises with the outside world

🟡 Same goal, different mechanics

An effect says: after this render commits, make the outside world (a subscription, a timer, a socket, a non-React widget) match these values. When the values change, React tears down the old sync and sets up the new one. Think in terms of start and stop syncing, not "on mount" and "on update". Ember's closest analogue is a modifier with registerDestructor, which also re-runs when its arguments change.

The dependency array

🟡 Same goal, different mechanics

The deps list every reactive value the effect reads: props, state, and anything derived from them. It's not a "run when X changes" knob you tune by hand. The react-hooks/exhaustive-deps lint rule is the source of truth. Leave it out and the effect runs after every render. Pass [] and it runs once per mount, which is only correct if it truly reads nothing reactive. If a dependency changes too often (an inline object or function), fix the value (move it inside the effect, memoize it, or use an Effect Event). Don't lie in the array.

Cleanup, and the Strict Mode double-invoke

🟡 Same goal, different mechanics

Return a function from the effect and React calls it before the next run and on unmount. Without cleanup, intervals keep ticking, listeners stack up and sockets leak.

In development, <StrictMode> deliberately mounts → unmounts → remounts every component, so every effect runs setup → cleanup → setup. That's a free test that your cleanup really undoes your setup, which also matters for <Activity>, Fast Refresh and future offscreen features. If the double run breaks something, the bug is in your effect, not in Strict Mode.

You might not need an effect

🔴 New mental model

Most effects in real codebases are unnecessary. Before writing one, check these:

  • Derived data: compute it in render (Day 3). An effect + setState means an extra render with stale UI first.
  • Event-driven logic: "when the user clicks Save, POST and show a toast" belongs in the event handler, not in an effect watching saved.
  • Resetting state when a prop changes: use key on the component.
  • Fetching data: use a data layer (Query, a router loader, or RSC). Day 9.

The test: is this synchronising with something outside React? If not, it's not an effect.

Race conditions: ignore stale responses

🟡 Same goal, different mechanics

Fetch in an effect, change issueId quickly, and responses can arrive out of order: the slow, stale one lands last and wins. Each effect run should own a flag that its cleanup flips, or an AbortController it aborts. ember-concurrency's restartable did this cancellation for you. Here the cleanup of the previous run is your cancellation point. (This is also why you'll use a data library for real fetching.)

useEffectEvent: read the latest values without re-syncing

🟡 Same goal, different mechanics

Sometimes an effect needs to read a value it shouldn't react to. Take a subscription that calls onNotify unless muted. Putting muted and onNotify in the deps would resubscribe on every toggle, and on every parent render (inline callbacks are new each time). Leaving them out makes the closure stale.

useEffectEvent (stable since React 19.2) wraps a function that always sees the latest props and state and doesn't belong in the deps. Call it only from inside effects.

Check yourself

Answer out loud first, then open the model answer.

1When do effects run?

After the render is committed and the browser has painted (useLayoutEffect runs before paint). On mount, the setup runs. On any later render where a dependency changed (by Object.is), the previous cleanup runs, then the new setup. On unmount, cleanup runs. Effects never run during server rendering.

2What is the dependency array really for?

It tells React which reactive values the effect's synchronisation depends on, so React can skip re-syncing when none changed. It must include every prop, state or derived value the effect reads; the lint rule enforces this. It's not a scheduling API. If you're tempted to omit something, the real fix is to restructure: move it inside the effect, memoize it, or read it through useEffectEvent.

3Why does Strict Mode run effects twice in development?

To surface missing or incorrect cleanup. It mounts, unmounts and remounts each component, so every effect goes setup → cleanup → setup. Correct effects behave the same as a single run. Leaky ones (double subscriptions, un-cleared timers, duplicated requests without a guard) become visible. It doesn't happen in production.

4How do you handle race conditions when fetching in an effect?

Give each effect run a way to know it's stale: a local let ignore = false set to true in cleanup, checked before setState, or an AbortController aborted in cleanup (which also cancels the network request). Better still, use a library (TanStack Query, router loaders) that keys requests and handles ordering, caching and dedupe for you.

5Name three cases where you don't need an effect.

1) Derived values: compute during render (useMemo if expensive). 2) Responding to user events: do the work in the event handler. 3) Resetting state when a prop changes: use a key. Also: notifying a parent about a state change (call the callback in the same handler), chaining state updates, and initialising app-wide singletons (module scope).

6What does useEffectEvent solve?

Reading the latest props or state inside an effect callback without making them dependencies. It separates "what we synchronise with" (deps) from "what we read when something happens" (the event). Typical uses: logging with the current user, notifying with the current muted flag, or calling the latest onX prop from a subscription. Rules: call it only from effects, never during render, and don't pass it to other components.

7How do effects compare to Ember modifiers?

Similar lifecycle: set up against something external, tear down when arguments change or on destroy. Differences: modifiers are bound to an element and are used in templates, while effects are bound to a component and are declared in its body. Effect re-runs are governed by an explicit deps array rather than autotracking. And effects run after paint, never during render. Ref callbacks with cleanup are the most direct "element modifier" equivalent.

Week 2 · Architecture · Day 6

Rendering performance: reconciliation, memoization, React Compiler

Glimmer updates what changed. React re-runs what might have changed, and lets you (or the Compiler) prove it didn't.

  1. 15 minConcepts
  2. 35 minHands-on
  3. 10 minCheck yourself

Concepts

Reconciliation: type + key

🔴 New mental model

React diffs element trees with two heuristics. Different type at the same position (<div> → <span>, ComponentA → ComponentB) means the old subtree is unmounted and the new one mounted, so its state is lost. Same type and same key means the instance is kept and its props updated.

So defining a component inside another component is a bug: every render creates a new function type, and the child remounts every time. Conditionally wrapping in an extra <div> resets the state of everything below it, for the same reason.

Parent renders → children render

🔴 New mental model

By default, when a component renders, every child it returns renders too, recursively, whether or not their props changed. That's usually fine, since renders are cheap and React only touches the DOM where output differs. It stops being fine with big lists, expensive children or high-frequency updates (typing, dragging). Glimmer never had this cost model, so it's easy to miss.

memo, useMemo, useCallback and referential stability

🔴 New mental model

memo(Component) skips a re-render when every prop is Object.is-equal to last time. It is defeated by any prop that's a fresh object, array or function on each render, such as onSelect={() => …} or style={{…}}.

  • useCallback(fn, deps) keeps the same function identity until the deps change.
  • useMemo(() => value, deps) does the same for computed values, and also caches expensive work.
  • Pass primitives where you can: isSelected={id === selectedId} instead of selectedId, so only the two rows whose boolean flipped re-render.

Memoization isn't free: there's comparison cost and memory, and it makes code noisier. Measure first.

Move state down, lift content up

🟢 Direct translation

Before memoizing, restructure. Move state down: put the draft input and its state in a <DraftNote/> component. Typing then re-renders only that component. Lift content up: if a stateful wrapper takes children, those children were created by its parent, so they don't re-render when the wrapper's state changes. These fixes are free and Compiler-proof.

React Compiler: auto-memoization

🔴 New mental model

The React Compiler (v1, stable) is a build-time Babel or Rust plugin. It analyses each component and hook and inserts fine-grained memoization: it caches JSX subtrees, derived values and callbacks keyed on their real inputs. It's effectively memo/useMemo/useCallback everywhere, done correctly. It relies on the Rules of React: components are pure, props and state are never mutated, and hooks are called unconditionally at the top level. It skips (or bails out of) code that breaks the rules.

Manual memo still matters for code the compiler can't see or bails out of, for values passed to non-React libraries that compare identity, for effect dependencies you want to be explicit about, and on codebases that haven't adopted it. Day 6's stretch goal turns it on.

Finding slow renders: the Profiler

🟡 Same goal, different mechanics

React DevTools → Profiler: record an interaction and see which components rendered, why ("props changed: onSelect"), and how long each took. Turn on "Highlight updates when components render". In code, <Profiler id onRender> reports commit timings, which is how the Day 5 and Day 6 tests count renders. Measure before memoizing: the slow thing is usually one component, not "React".

1Does a re-render mean a DOM update?

State architecture: Context, reducers, external stores

There is no container. "Services" are values placed in the tree, and a context is a transport, not a store.

  1. 15 minConcepts
  2. 35 minHands-on
  3. 10 minCheck yourself

Concepts

Services → Context + a provider

🟡 Same goal, different mechanics

An Ember service is a lazily created singleton from the DI container, available anywhere with @service. React has no container. createContext defines a slot, a provider puts a value into the tree, and useContext (or use(Context)) reads the nearest provider above. Scope comes from where you render the provider: two providers give two independent "services", which is great for tests and for embedding.

Context is dependency injection, not state management. It carries whatever you put in it: a reducer's state, a store, a client. In React 19, <MyContext value={…}> is the provider; .Provider is no longer needed.

Every consumer re-renders when the value changes

🔴 New mental model

When a provider's value changes (by Object.is), every component that reads that context re-renders, even if it only uses one field, and even if it's wrapped in memo. There's no selector. Two consequences:

  • Memoize the value object. value={{ issues, dispatch }} is a new object on every provider render, so every consumer re-renders every time.
  • Split contexts by update frequency: put dispatch (stable) in one, issues (changes) in another, and the theme in a third. Or put a store in context and subscribe with selectors.

useReducer

🟢 Direct translation

useReducer(reducer, initial) moves the update logic into a pure (state, action) => newState function, the same as Redux. You can test it without React, it centralises the transitions, and dispatch has a stable identity (good for context). Use it when the next state depends on the previous state in several ways, or when updates are naturally named events (added, statusChanged). Throw on unknown actions, and type actions as a discriminated union for exhaustiveness.

External stores with useSyncExternalStore

🟡 Same goal, different mechanics

For state shared widely and updated often, keep it outside React and subscribe with a selector: useSyncExternalStore(subscribe, getSnapshot). A component re-renders only when its selected snapshot changes. It also prevents tearing: during a concurrent render, React makes sure every component sees the same version of the store. This is the primitive under Zustand, Redux (useSelector), Jotai and friends.

The snapshot must be stable for unchanged data: return a slice, not a fresh object or array on each call.

Where should state live?

🟡 Same goal, different mechanics

Escalate only as needed:

  • Local useState in the component that uses it.
  • Lifted to the nearest common parent when siblings share it.
  • URL for anything that should survive reload or be shareable: filters, tabs, selection (Day 10).
  • Context for tree-wide, low-frequency values (current user, theme, feature flags) or for injecting a client or store.
  • External store (Zustand, Redux) for high-frequency, app-wide client state with many readers.
  • Server cache (TanStack Query, loaders) for anything that comes from the server, which is usually most of your "state" (Day 9).

1How does Context compare to an Ember service?

Both inject shared things without prop drilling. A service is a container-managed singleton: lazily created, globally addressable by name, and fine-grained reactive through @tracked. Context is tree-scoped: the value comes from the nearest provider above, and there can be many providers. State lives in whatever you put in it (useReducer, a store, a client).

2Why can context cause performance problems?

Every consumer re-renders whenever the provider's value changes by reference, regardless of which part it uses, and memo doesn't help. Common causes are an un-memoized object literal as the value, or one giant context holding fast-changing state. 3useReducer vs useState?

They're the same mechanism (useState is a reducer that replaces the state). Use useReducer when there are several related fields or transitions, when the next state depends on the previous state in non-trivial ways, when you want the logic as a pure, testable function, or when you want a stable dispatch to pass down instead of many callbacks. Subscribing safely to state that lives outside React. Without it, a concurrent render could read the store at different moments for different components and show inconsistent UI (tearing). 5When would you reach for Zustand or Redux?

When client state is shared across distant parts of the tree, updated often, and read by many components, so context would cause broad re-renders: editors, canvases, complex UI state, multi-step workflows. Redux (Toolkit) adds strict conventions, devtools and middleware for large teams. Zustand is minimal. Not for server data: that belongs in a server cache.

Custom hooks

A hook is just a function that calls hooks. That makes it the unit of reuse for stateful logic.

  1. 15 minConcepts
  2. 35 minHands-on
  3. 10 minCheck yourself

Concepts

Hooks are the unit of reusable stateful logic

🟡 Same goal, different mechanics

A custom hook is a function named useX that calls other hooks. It can own state and effects and return anything: values, setters, tuples, objects. Each call site gets its own state. Nothing is shared unless the hook reads a context or an external store.

Ember spread this across ember-resources (reactive values with teardown), stateful helpers, and services for shared state. In React they're all custom hooks.

The Rules of Hooks, and why

🔴 New mental model

Call hooks only at the top level of a component or custom hook: never in conditions, loops, nested functions or after an early return. Call them only from React functions.

Why: React stores hook state in a list on the component instance and matches it up by call order. Hook #1 is the first useState, hook #2 the next, and so on. If a condition skips a hook on one render, every later hook reads the wrong slot. There are no names or keys, only order. (use() is the exception: it may be called conditionally.)

Composing hooks

🟡 Same goal, different mechanics

Hooks compose like functions: useIssueSearch = useLocalStorage (persisted query) + useDebouncedValue (settled query) + a derived filter. Keep each hook small, return stable identities (useCallback) for anything a consumer might pass to memo or effect deps, and derive rather than store.

Testing hooks with renderHook

🟢 Direct translation

renderHook(() => useThing(args), { initialProps, wrapper }) mounts a throwaway component and gives you result.current. Wrap state changes in act(), call rerender(newProps) to change inputs, and use wrapper for providers (a QueryClient, a context). Use fake timers for debounce and intervals. Better still, test hooks through a component when the hook only exists to serve that component.

1Why can't hooks be called conditionally?

React identifies each hook's state by its position in the call order during a render, not by name. If a hook is skipped or added conditionally, every later hook shifts slots and reads another hook's state. That means corrupted state and React's "rendered fewer/more hooks than expected" error. 2Do two components using the same hook share state?

No. Each call creates independent state in that component's instance. A hook shares logic, not data. To share data, the hook must read from something shared: a context, an external store (useSyncExternalStore), a server cache (TanStack Query, where two useQuery calls with the same key do share the cache), or module-level state.

3Hooks vs HOCs vs render props?

All three reuse behaviour. HOCs (withX(Component)) wrap components. They're hard to type, create wrapper hell and cause prop-name collisions, so they're mostly legacy. Render props invert control over markup, which is still useful when a child owns per-item data. Hooks reuse stateful logic with no extra components, compose naturally and type cleanly. Hooks are the default today.

4How do you test a custom hook?

Prefer testing through the component that uses it (behaviour over implementation). For reusable library hooks, use renderHook from Testing Library: assert on result.current, drive changes with act() and rerender(), provide context with wrapper, and control time with fake timers. Week 2 · Architecture · Day 9

Data fetching: TanStack Query, Suspense, error boundaries

Server state is a cache you don't own. Stop putting it in useState.

  1. 15 minConcepts
  2. 35 minHands-on
  3. 10 minCheck yourself

Concepts

Server state ≠ client state

🟡 Same goal, different mechanics

Client state (UI toggles, form drafts) is synchronous, owned by you, and always current. Server state is remote, asynchronous, shared and possibly stale the moment you receive it. It needs caching, dedupe, background refetch, invalidation after writes, retries and pagination. Hand-rolling that with useEffect + useState is how codebases accumulate race conditions (Day 5). Use a server-cache library: TanStack Query, router loaders, or RSC.

The query cache vs the ember-data store

🟡 Same goal, different mechanics

TanStack Query caches by query key, not by type + id. There's no normalisation and no identity map: ['issues','list',{status:'todo'}] and ['issues','detail','1'] are separate entries that both contain issue 1. You keep them consistent by invalidating related keys after a mutation, or by writing to them with setQueryData.

Defaults to know: staleTime: 0 (data is stale immediately, so remounting, refocusing or reconnecting refetches in the background while the cached data shows: stale-while-revalidate), gcTime: 5 min for unused entries, 3 retries, and identical in-flight requests deduped. ember-concurrency's isRunning / last.error map to isPending / isFetching / isError / error.

Query-key factories

🟢 Direct translation

Keys are arrays, compared structurally and hierarchically. Invalidating ['issues'] hits every key that starts with it. Centralise them in a factory so components never hand-write keys, and include every input of the queryFn in the key (filters, ids, page). If it isn't in the key, different inputs share one cache entry.

Mutations and invalidation

🟡 Same goal, different mechanics

useMutation({ mutationFn, onSuccess }) gives you mutate/mutateAsync, isPending and error. After a successful write, invalidate the affected keys. Active queries refetch and inactive ones are marked stale. Return the invalidation promise from onSuccess to keep the mutation pending until the fresh data has arrived. For instant UI, do an optimistic update: onMutate writes the cache, onError rolls back, onSettled invalidates.

Suspense for data

🔴 New mental model

With Suspense, a component that isn't ready suspends: it throws a promise (or calls use(promise)), and the nearest <Suspense fallback> above it shows the fallback until the promise settles. useSuspenseQuery does this for you, and data is then always defined. Loading UI moves out of the component and up the tree, where you choose the granularity. Errors work the same way: thrown, then caught by the nearest error boundary.

Caveats: sibling suspending queries inside one component run in series (a waterfall), so hoist or prefetch them. Promises passed to use() must be cached, not created during render.

Error boundaries are still class components

🔴 New mental model

There's still no hook for catching render errors. An error boundary is a class with static getDerivedStateFromError (switch to the fallback) and optionally componentDidCatch (report the error). It catches errors thrown during render, lifecycle and effects of its subtree. It does not catch errors in event handlers or async code you didn't render with, which you handle yourself. Most apps use the react-error-boundary package. With Query, wrap it in QueryErrorResetBoundary so "Try again" clears the cached error and refetches.

1Server state vs client state?

Client state is owned by the UI: synchronous, always correct, private (open menus, drafts, selection). Server state is owned by the server: async, shared, and stale as soon as it's fetched, so it needs caching, background refresh, dedupe, invalidation after mutations and error/retry handling. Treating server data as client state (copying it into useState) is the root of most data bugs. Keep it in a server cache and derive from it.

2What is stale-while-revalidate?

Serve cached data immediately, even if stale, while refetching in the background, then swap in the fresh result. In TanStack Query, data becomes stale after staleTime (default 0). When a stale query is used again (mount, window focus, reconnect, invalidation), it shows the cached data with isFetching: true and refetches. Users see instant UI and eventual freshness.

3How do query keys work?

A key is a serialisable array that uniquely identifies a cache entry. It's hashed deterministically (object key order doesn't matter) and matched by prefix for invalidation. Every input to the queryFn must be in the key, so different inputs give different entries. Key factories keep them consistent and make hierarchical invalidation (['issues'] → all lists and details) easy.

4Optimistic update vs invalidation?

Invalidation: after the server confirms, mark the related keys stale and refetch. Always correct, and the UI updates after a round trip. Optimistic: update the cache (or show useOptimistic state) before the server answers, roll back on error, and usually invalidate on settle to reconcile. It feels instant, but you need rollback logic and you risk briefly showing something false. Use optimistic updates for high-confidence, low-stakes interactions (toggles, likes, reordering).

5How does Suspense work?

During render, a component that needs unavailable data suspends: it throws a promise (libraries do this for you), or calls use(promise). React stops rendering that subtree and shows the nearest <Suspense> fallback. When the promise resolves, React retries the render. Already-visible content isn't replaced by a fallback for updates made inside a transition. On the server, Suspense boundaries are streaming points.

6Why aren't error boundaries hooks?

Catching an error thrown while rendering children requires a component that can render a different tree in response, in the same commit, after a child failed. That ties into class lifecycle hooks (getDerivedStateFromError, componentDidCatch) that have no hook equivalent yet. In practice you write one class, or use react-error-boundary, and compose it like any component.

7How does this compare with ember-data?

ember-data/WarpDrive is a normalised identity map: one record per type + id, relationships, and a single source of truth that every view shares. TanStack Query is a request cache keyed by query, with no normalisation. You keep views consistent through invalidation or setQueryData. That's simpler and protocol-agnostic, but consistency is explicit. Query's lifecycle features (stale-while-revalidate, focus refetch, retries, dedupe, gc) are richer out of the box. WarpDrive's newer request-centric APIs are converging on the same model.

Router.map → route objects

🟢 Direct translation

In data mode you declare routes as objects: { path, element, loader, errorElement, children }. Nested routes and {{outlet}} → <Outlet/>

🟢 Direct translation

A parent route renders <Outlet/> where its matched child goes, exactly like {{outlet}}. Layouts persist across child navigations, so their state survives. An index: true route renders at the parent's own URL (Ember's index route).

The model hook → loader + useLoaderData

🟢 Direct translation

A loader({ params, request }) runs before the route renders, and all matched loaders run in parallel (Ember resolves models parent-first, in series). The component reads the result with useLoaderData(). Type it with useLoaderData<typeof loader>(). Search params live on new URL(request.url). Loaders re-run on navigation and after actions, and you can redirect() or throw from them.

Error and loading substates → errorElement and useNavigation()

🟢 Direct translation

Throw from a loader (or render) and the nearest route's errorElement renders in place of that route's element. Parents (and the list next to a failing detail) stay on screen. Throw data('Not found', { status: 404 }) for HTTP-style errors, and check them with isRouteErrorResponse(error).

There are no loading substates by default: the old page stays while the next one loads, and useNavigation().state === 'loading' lets you show a global pending indicator. That's usually better UX than flashing a spinner page.

🟡 Same goal, different mechanics

const [searchParams, setSearchParams] = useSearchParams(). Reading gives you a URLSearchParams. Setting it navigates, which re-runs loaders. Use useNavigate() for programmatic transitions (router.transitionTo). Relative paths resolve against the route hierarchy. React 19 Actions & concurrent features

Transitions mark updates as interruptible, and Actions are async transitions with pending, error and optimistic state built in. This is the closest React gets to ember-concurrency.

  1. 15 minConcepts

  3. 10 minCheck yourself

Concepts

Transitions: urgent vs non-urgent updates

🔴 New mental model

Every update has a priority. Typing, clicking and hovering are urgent: the UI must respond immediately. Re-rendering a big filtered list or switching tabs can wait. startTransition(() => setX(…)) marks an update as a transition: React renders it in the background, keeps showing the current UI, interrupts the work if something urgent happens, and won't replace visible content with a Suspense fallback. useTransition() also gives you isPending.

Ember has no equivalent. Rendering there is synchronous inside the runloop.

Actions: <form action>, useActionState, useFormStatus

🔴 New mental model

In React 19, a transition can be async: that's an Action. Pass an async function to <form action={fn}> and React calls it with the FormData, inside a transition, and resets uncontrolled fields when it finishes. useActionState(action, initial) wraps it: it gives you [state, formAction, isPending], where state is whatever the action returned last (a result or an error), and it queues submissions in order. useFormStatus() lets any component inside the form read pending without prop drilling.

This replaces the useState × 3 + onSubmit + try/finally boilerplate. The same Actions run as Server Functions (Day 12).

useOptimistic

🔴 New mental model

const [optimistic, addOptimistic] = useOptimistic(actual, reducer?) returns actual, except while a transition is pending, when it returns the optimistic value you set. When the transition settles, React drops the optimistic layer and shows actual again. On success you've updated actual, so nothing visibly changes. On failure you haven't, so the optimistic value just disappears: rollback comes for free. Call addOptimistic inside startTransition or an Action.

useDeferredValue

🟡 Same goal, different mechanics

const deferred = useDeferredValue(query) returns a value that lags behind during heavy renders. React first re-renders urgently with the old deferred value (the input stays responsive), then renders with the new one in the background, abandoning that render if query changes again. Unlike debouncing, there's no fixed delay: on a fast device it's instant, and on a slow one it adapts. It doesn't reduce network calls, though. For requests, you still debounce.

ember-concurrency, mapped

🟡 Same goal, different mechanics
  • task.perform() → an Action or startTransition(async …)
  • task.isRunning → isPending (useTransition, useActionState, useFormStatus, Query's isPending)
  • task.last.value / .error → useActionState's state, or the mutation's data / error
  • restartable (cancel the previous one) → effect cleanup or AbortController; Query cancels for you
  • enqueue → useActionState (submissions queue in order)
  • drop → disable the button while pending, or check isPending
  • timeout() debounce → useDeferredValue (render) or a debounced value (network)

<ViewTransition> (stable in 19.3)

🟢 Direct translation

Wrap content in <ViewTransition> and updates made in a transition (startTransition, Actions, router navigations) animate through the browser's View Transitions API: a cross-fade by default, customised with CSS (::view-transition-*) or by name for shared-element morphs. addTransitionType('forward') tags a transition so CSS can vary per type. Urgent updates don't animate, which is one more reason to use transitions for navigations.

1What is a transition?

An update marked as non-urgent with startTransition or useTransition. React renders it concurrently: it can be interrupted by urgent updates (typing), it keeps the current UI interactive, it avoids replacing already-visible content with Suspense fallbacks, and it reports isPending. Since React 19 transitions can be async, which makes them Actions.

2What problem do Actions solve?

The boilerplate and the bugs around async mutations: tracking pending state, sequencing submissions, handling errors, resetting forms, optimistic UI. An Action is an async function run in a transition. React tracks its pending state (useActionState, useFormStatus), queues repeated submissions, integrates with useOptimistic, resets uncontrolled forms on success, and the same model works for Server Functions with progressive enhancement.

3useActionState vs useState + onSubmit?

With useState + onSubmit you manage isSubmitting, error and result yourself, remember preventDefault, guard against double-submits and order async results by hand. useActionState returns the last result as state plus isPending, runs the action in a transition, queues calls so results arrive in order, receives FormData directly, and (when given a server function) works before hydration via a permalink. Less code, fewer race conditions.

4How does useOptimistic roll back?

It doesn't keep a snapshot. The optimistic value is a temporary layer that only exists while the surrounding transition is pending. When the transition ends, React renders from the real state again. If the server call succeeded you updated the real state, so the UI stays put. If it failed you didn't, so the optimistic value simply disappears. You only need to surface the error.

5useDeferredValue vs debouncing?

Debouncing delays the update by a fixed time, even on fast devices, and it's still the right tool for limiting network requests. useDeferredValue updates immediately at low priority. React renders the urgent UI first, then the deferred render in the background, interrupting it if the value changes again. There's no arbitrary delay, it adapts to device speed, and the input never janks. It doesn't reduce how often expensive work is attempted, only how it's scheduled.

Server Components & the Next.js App Router

The biggest model shift in the course. Components can run only on the server, and the boundary between server and client is something you design.

  1. 15 minConcepts
  2. 35 minHands-on
  3. 10 minCheck yourself

Concepts

React Server Components

🔴 New mental model

A Server Component runs only on the server (at request time or build time) and never ships its code to the browser. It can be async and await data directly: the database, the filesystem, secrets. It can't use state, effects, refs, browser APIs or event handlers, because it never re-renders on the client. Its output is serialised (the RSC payload) and merged into the client tree. In the App Router, components are server components by default.

'use client' marks a boundary, not "client-only"

🔴 New mental model

'use client' at the top of a file says: this module, and everything it imports, is part of the client bundle. Client components still render on the server (SSR) for the initial HTML, then hydrate. The directive marks the entry point where the server tree hands over to interactive code. You only need it on the boundary file, not on every component below it.

Props crossing the boundary must be serialisable: primitives, plain objects and arrays, Dates, Maps and Sets, promises, JSX, and Server Functions. Regular functions and class instances can't cross. Server components can be passed through client components as children.

Server Functions ('use server')

🔴 New mental model

A function in a 'use server' module (or with the directive in its body) becomes a Server Function. The client gets an opaque reference, and calling it makes a POST that runs the function on the server. Pass one to <form action> and the form works before JS loads (progressive enhancement). Pair it with useActionState for results and pending state. Its arguments come from the network, so treat it as a public API endpoint: validate the input, check auth.

Streaming + Suspense

🔴 New mental model

On the server, every <Suspense> boundary is a streaming point. React sends the shell HTML right away with the fallbacks, then streams each boundary's HTML (and RSC payload) as its data resolves, inlined into the same response. Slow data no longer blocks the whole page. Client components inside hydrate selectively, prioritising whichever part the user interacts with. In Next.js, loading.tsx is a Suspense boundary around a route segment.

SSR vs RSC vs FastBoot

🟡 Same goal, different mechanics
  • SSR (classic): render the client app to HTML on the server, then ship all of its JS and hydrate. FastBoot is this.
  • RSC: some components exist only on the server. Their code and dependencies never ship, and their output arrives as a serialised tree. RSC is orthogonal to SSR: you usually do both (RSC builds the tree, SSR turns it into HTML for first paint).
  • Benefit: less JS, direct data access, no client-server waterfalls. Cost: a server runtime, a mental boundary, and a bundler/framework (Next.js, React Router framework mode, Waku).

React 19.3: Server Components can render a <Context> provider directly. Providers no longer need their own 'use client' wrapper file, although only client components can read context.

Where the Next.js App Router fits

🟡 Same goal, different mechanics

File-system routes under app/. layout.tsx is a persistent wrapper (your application.hbs / parent route), page.tsx is a route's UI, and loading.tsx and error.tsx are Suspense and error-boundary substates. Pages are server components that receive params and searchParams as Promises (Next 15+): const { status } = await searchParams. Mutations use Server Functions plus revalidatePath / revalidateTag, and the client router caches RSC payloads between navigations.

1RSC vs SSR?

SSR renders client components to HTML on the server for a fast first paint, then ships all of that code to the browser to hydrate. RSC introduces components that run only on the server. Their code never ships, they can access server resources directly, and their output is a serialised React tree, not HTML. They're complementary: frameworks use RSC to build the tree and SSR to turn it into initial HTML. RSC reduces bundle size and client waterfalls. SSR improves first paint.

2What does 'use client' actually mean?

It marks a module as a client entry point: the boundary where the server module graph hands over to modules that are bundled for the browser. That file and everything it imports become client code, which is still SSR'd and then hydrated. It doesn't mean "skip SSR", and it isn't needed on every interactive component, only at the boundary. Props passed into it from the server must be serialisable.

3Why can't you pass a function from a server component to a client component?

Server and client run in different environments, separated by a network. Props crossing the boundary are serialised into the RSC payload, and closures can't be serialised: they capture server scope and code that never ships. The exception is a Server Function ('use server'), which is passed as a reference ID the client can invoke over the network. Pass data, JSX (children) or server functions, never plain callbacks.

4How do Server Functions work?

The bundler replaces each exported function in a 'use server' module with a reference (an ID plus the endpoint) in client code. When the client calls it, or a form submits to it, React serialises the arguments and POSTs them. The framework runs the real function on the server and serialises the result back. In Next.js the response can also carry an updated RSC payload after revalidatePath. Forms with a Server Function action work before hydration. They are public endpoints: authenticate and validate every call.

5When would you not use RSC?

Highly interactive, client-state-heavy apps (editors, canvases, offline-first tools, dashboards behind auth with little SEO need), where most components would be 'use client' anyway. Also when you can't or don't want to run a Node server (static hosting, an existing non-JS backend), when the team or tooling isn't ready for the boundary model, or for embedded widgets. A well-built SPA with a server cache is still a valid architecture.

Testing React well

Same philosophy as @ember/test-helpers: test what the user sees. The difference is that nothing waits for "settled". You wait for the outcome.

  1. 15 minConcepts
  2. 35 minHands-on
  3. 10 minCheck yourself

Concepts

@ember/test-helpers → Testing Library

🟢 Direct translation

render(<Comp/>) mounts into a container attached to document.body. screen.* queries the document. userEvent drives real event sequences. Assertions come from @testing-library/jest-dom (toBeInTheDocument, toHaveAttribute, toBeVisible). It's the same "test like a user" philosophy as @ember/test-helpers + qunit-dom. React has no container or owner to set up. You wrap the component in whatever providers it needs (a QueryClient, a router, context).

Query priority

🟢 Direct translation

In order: getByRole (with name) → getByLabelText → getByPlaceholderText → getByText → getByDisplayValue → getByAltText / getByTitle → getByTestId as a last resort. Role queries check what assistive tech sees. If you can't find an element by role and name, a screen reader user probably can't either. Variants: getBy (throws if missing), queryBy (returns null, for asserting absence) and findBy (async, waits).

userEvent vs fireEvent

🟢 Direct translation

fireEvent.click(el) dispatches one synthetic DOM event. userEvent.click(el) simulates the whole interaction: pointer events, mousedown, focus change, mouseup, click. It also respects disabled and pointer-events, and user.type fires per-key events. Always const user = userEvent.setup() and await every call. Reach for fireEvent only for events that userEvent doesn't model.

findBy / waitFor vs await settled()

🟡 Same goal, different mechanics

Ember's test waiters track the runloop, pending AJAX and timers, so await settled() waits until everything is idle. React has no global settled state. Instead you wait for the outcome you expect: await screen.findByRole(…) retries until the element appears (1 s default), and await waitFor(() => expect(…)) retries an assertion. act() flushes React's own work and is already wrapped around render, userEvent and RTL's async utilities. Don't wrap those in act yourself.

Fake timers: vi.useFakeTimers() + act(() => vi.advanceTimersByTime(ms)).

Mocking the network: MSW

🟢 Direct translation

Mock at the network boundary, not at the module boundary. Mock Service Worker intercepts fetch in Node and in the browser, so your real data layer (Query, loaders) runs unchanged. That's the closest thing to Mirage, with handlers per test (server.use(http.get(…))). This course uses an in-memory fake API instead, so the exercises stay dependency-free.

Test behaviour, use accessibility as the strategy

🟢 Direct translation

A good test survives a refactor that doesn't change behaviour, and fails when behaviour breaks. Avoid asserting state values, hook calls, class names you don't need, component internals or snapshot blobs. Query by role, name and state (selected, expanded, pressed), drive with the keyboard, and you're testing accessibility for free. The Day 13 exercise turns this into a measurement: your tests are only as good as the bugs they catch.

1Why prefer getByRole?

It queries the accessibility tree, the same thing assistive technology uses, by role and accessible name. That makes tests resilient to markup and styling changes, documents intent ("the Save button"), and fails when accessibility breaks (a missing label, the wrong role). If an element can't be found by role, that's often a real a11y bug.

2What's wrong with testing implementation details?

Such tests break on refactors that don't change behaviour (false negatives that erode trust) and pass when behaviour is broken (false positives). Examples: asserting on component state, calling instance methods, checking which hook was used, shallow rendering, or snapshotting markup. Test inputs and outputs the user or caller can observe: rendered text and roles, focus, callbacks invoked, network effects.

3waitFor vs findBy?

findBy* is waitFor + getBy*. It retries a query until an element appears or the timeout passes. Use it to wait for something to appear. waitFor(cb) retries any callback until it stops throwing. Use it for other assertions (disappearance, call counts, db state). Keep waitFor callbacks side-effect-free, with one assertion each, and never put userEvent calls inside them.

4How do you test a component that fetches?

Render it with its real data layer (a fresh QueryClient per test with retry: false, or a memory router for loaders) and mock the network, using MSW or a fake API, not the hook. Assert the loading state, then await findBy… for the data, and cover the error path (a handler returning 500, then "Retry"). Isolate tests with fresh caches and handlers reset between them.

5How do you test a custom hook?

Ideally through a component that uses it. For reusable hooks, use renderHook(() => useX(props), { initialProps, wrapper }), read result.current, change inputs with rerender, trigger updates in act(), and use fake timers for time-based hooks. Assert observable results (returned values, side effects such as storage), not internal state.

6What makes a test flaky?

Hidden dependence on timing or shared state: fixed setTimeout sleeps instead of waiting for an outcome, forgetting to await userEvent or findBy, leaking state between tests (a shared QueryClient, module singletons, unrestored fake timers, leftover listeners), real network calls, animation or transition timing, and order-dependent tests. Patterns, TypeScript & modern APIs

Patterns you already know from Ember, in React's vocabulary, plus the APIs React 19 added.

  1. 15 minConcepts
  2. 35 minHands-on

Concepts

Compound components via context

🟡 Same goal, different mechanics

<Accordion><Accordion.Item><Accordion.Trigger/>… gives the caller full control of the markup while the parent owns the state. The parent provides state through context, and each part reads it (and throws a helpful error outside a parent). That's the React spelling of yielding contextual components with hash. Attach the parts with Object.assign(Root, { Item, Trigger, Panel }).

Portals

🟡 Same goal, different mechanics

createPortal(jsx, domNode) renders children into another DOM node, usually document.body, so modals, toasts and popovers escape overflow: hidden and stacking contexts. The surprise: in the React tree the portal is still a child of the component that rendered it. Context flows into it, and synthetic events bubble to React ancestors, not DOM ancestors. Don't stopPropagation inside a dialog just to stop backdrop clicks: check e.target === e.currentTarget on the backdrop instead. (Also consider the native <dialog> element with showModal().)

ref is just a prop now

🟢 Direct translation

In React 19, function components receive ref like any other prop, so forwardRef is obsolete (still supported, slated for deprecation). Type it with ComponentProps<'input'>, which already includes ref, and pass it on to the element. Ref callbacks can return a cleanup function, so a ref callback is now a complete "element modifier".

<Activity>: hide without unmounting

🔴 New mental model

Conditional rendering unmounts: state, DOM and scroll position are gone. <Activity mode="hidden"> (stable since 19.2) keeps the subtree mounted but hidden (display: none), preserves its state and DOM, unmounts its effects (subscriptions pause) and renders updates to it at the lowest priority. mode="visible" restores it instantly, with effects re-mounted. Use it for tabs, back/forward caches and pre-rendering the likely next screen.

Typing components

🟡 Same goal, different mechanics
  • Extend native props: ComponentProps<'button'> (or ComponentPropsWithoutRef when you omit ref) and Omit<…, 'onChange'> when you change a signature.
  • Generic components: function Select<T>({ items, getLabel, onChange }: SelectProps<T>). TypeScript infers T from usage. In .tsx, arrow generics need <T,>.
  • Discriminated-union props make invalid combinations unrepresentable: { variant: 'link'; href: string } | { variant: 'button'; onClick(): void }.
  • ReactNode for anything renderable, ReactElement only when you must have an element.

Ember's Glint gave you template type-checking. With JSX it's just TypeScript.

Fragment refs and <ViewTransition> (19.3)

🔴 New mental model

Fragment refs (stable in 19.3): <Fragment ref={ref}> gives you a FragmentInstance that addresses all of its first-level DOM children without a wrapper element: addEventListener, observeUsing(intersectionObserver), getClientRects(), focus(). That's useful for visibility tracking and focus management around arbitrary children. <ViewTransition> (Day 11) animates transition-driven updates with the View Transitions API.

1What are compound components, and how do you build them?

A set of components that work together under a parent, such as <Tabs><Tabs.List><Tabs.Tab/>…, sharing implicit state. The caller composes the markup freely and the parent owns the behaviour. 2Why portals, and how do events bubble through them?

A click inside a portal reaches the onClick of the React component that rendered it, even though DOM-wise it's elsewhere. Context also flows through. 3What changed with refs in React 19?

Conditional rendering unmounts the hidden branch, which destroys its state and DOM and runs effect cleanups. Use Activity when returning to a view should be instant and stateful. Use conditional rendering when hidden UI should really go away.

1Walk me through what happens when setState is called.Rendering

The setter enqueues an update on that component's fiber with a priority (lane). In an event it's batched with others, and it's lower priority inside a transition. React schedules a render. During render it walks down from the root, re-running the updated component and (by default) its descendants. Memoized subtrees bail out when their props are Object.is-equal. The new state is computed by applying the queued updates in order. React reconciles the new elements against the current fiber tree (type + key) and collects DOM mutations. Concurrent renders can be interrupted. Then commit: apply the DOM changes synchronously, attach refs, run layout effects, paint, then run passive effects (useEffect). If the new state is Object.is-equal to the old, React can bail out early.

2React has no fine-grained reactivity. Why is it still fast enough, and when isn't it?Rendering

Re-rendering is a JS function call plus a diff of lightweight element objects. DOM work, which is the expensive part, happens only where output changed. Batching collapses updates, concurrent rendering keeps input responsive during heavy work, and the React Compiler auto-memoizes to skip unchanged subtrees. It struggles with very large trees re-rendering on high-frequency updates (typing in a big form, dragging) and with expensive render functions. Fix those with state colocation, memoization, useDeferredValue, virtualisation, or an external store with selectors.

3How do keys affect component identity and state?Components

React matches children between renders by type and key. Same type and key: the instance is reused with its state, refs and DOM. A different key means unmount and remount. Index keys tie state to positions, so reordering moves state to the wrong items. Stable data ids prevent this, and changing a key on purpose resets a component (<Form key={id}/>).

4How would you design a reusable Select that works with any item type?Components

A generic component, Select<T>, with items: T[], getKey, getLabel and value / onChange typed by T. Make it controlled with an optional uncontrolled default, accessible (a listbox/combobox pattern or native <select>), and compositional (render props or compound parts for custom options), with native props passed through to the trigger and ref as a prop. Ideally it's built on a headless library (React Aria, Radix, Ariakit) so keyboard handling and a11y are solved.

5How would you structure state in a large app?State

By ownership and lifetime, not by "global vs local". Server state goes in a server cache (TanStack Query, or loaders/RSC), which is usually most of it. URL state (filters, tabs, selection, pagination) goes in the router. Local UI state stays colocated in components and is lifted only as far as needed. Cross-cutting client state (auth session, preferences, complex editors) goes in context for low-frequency values, or an external store with selectors (Zustand/Redux) for high-frequency, widely read values. Derive rather than duplicate, keep a single source of truth per fact, use reducers for complex transitions, and put feature boundaries around providers.

6Why is mutating state a bug, even when the UI seems to update?State

React decides whether to re-render by reference equality. A mutated object is the same reference, so memo, useMemo, effect deps and bail-outs treat it as unchanged. The UI only appeared to update because something else triggered a render. Mutation also corrupts the previous render's snapshot (breaking concurrent rendering, transitions and Strict Mode double renders) and makes behaviour depend on timing.

7Controlled or uncontrolled for a 30-field settings form?Events & forms

Mostly uncontrolled: native inputs with defaultValue, read via FormData in a form Action, and validation on submit or blur (with native constraints plus a schema). Controlled re-renders the form on every keystroke and needs a state field per input. Use controlled fields only where other UI depends on the live value. Or use a form library (React Hook Form is uncontrolled and ref-based) for field arrays, dirty tracking and validation.

8How do React events differ from native DOM events?Events & forms

They're synthetic wrappers dispatched via delegation from the root container, propagating through the React component tree (including through portals). The handlers are props. onChange fires on every input, unlike the native change event. e.nativeEvent gives you the original. stopPropagation stops React propagation, and native listeners on ancestors may still see the event depending on attachment. Return values don't prevent defaults: call preventDefault().

9When is useEffect the right tool, and when is it a code smell?Effects

It's right for synchronising with external systems keyed on props or state: subscriptions, timers, non-React widgets, imperative DOM APIs, analytics on visibility. It's a smell when it computes derived state, responds to user events (put that in the handler), resets state on prop change (use key), fetches without a race guard or cache (use a data library), or chains state updates. Rule of thumb: if there's no external system, there's no effect.

10Explain stale closures with an example, and how you avoid them.Effects

Each render's functions capture that render's props and state. A setInterval(() => setCount(count + 1), 1000) created in an effect with [] deps keeps seeing count = 0 forever. Avoid it with updater functions (setCount(c => c + 1)), correct dependency arrays (re-subscribe when inputs change), useEffectEvent for reading the latest values in an effect callback without re-syncing, or a ref holding the latest value for imperative code.

11When do you use memo, useMemo and useCallback, and what changes with the React Compiler?Performance

Without the compiler: memo for components that re-render often with the same props and are expensive (list rows, charts). useCallback and useMemo to keep the props to those components stable, to cache expensive computations, and to stabilise effect deps. Measure first. With the compiler, most of this is automatic and you remove manual memoization. You still care about code the compiler skips (rule violations), identity for third-party libraries, and architectural fixes (state colocation, virtualisation), which no compiler does for you.

12A list of 5,000 issues stutters when typing in its filter. What do you do?Performance

Profile first. Then: keep the input responsive with useDeferredValue (or startTransition) for the filter applied to the list. Virtualise the list (TanStack Virtual) so only visible rows render. Memoize rows with stable props (or let the compiler do it). Make the filter itself cheap (precompute lower-cased titles with useMemo). And, if the data allows, move filtering server-side with debounced queries.

13Context vs an external store vs TanStack Query: how do you choose?Architecture

Query for anything fetched from a server: caching, invalidation and background refresh. Context for injecting dependencies and low-frequency tree-wide values (theme, user, a client instance), because every consumer re-renders on change. An external store with selector subscriptions (Zustand/Redux via useSyncExternalStore) for frequently changing client state shared across distant components. These are often combined: context provides a store, and components select from it.

14What is tearing, and how does React prevent it?Architecture

Tearing is when one render shows inconsistent versions of the same external data, because a concurrent render yielded mid-way and the store changed in between, so some components read the old value and some the new. useSyncExternalStore prevents it by checking snapshots during render and forcing a synchronous re-render if the store changed during a concurrent render. React-managed state (useState/context) can't tear.

15Why do the Rules of Hooks exist?Hooks

React associates hook state with a component by call order, not by name. Calling hooks conditionally, in loops or after early returns changes that order between renders, so state is read from the wrong slot. The rules (top level only, only from components and hooks) keep the order stable. The lint plugin enforces them, and the Compiler relies on them.

16Design a useFetch(url) hook. Then tell me why you wouldn't ship it.Hooks

State { data, error, status }. An effect on [url] with an AbortController (or an ignore flag) cleaned up on change, that sets state on resolve or reject, and resets to loading when the url changes. I wouldn't ship it because it lacks caching and dedupe across components, background revalidation, invalidation after mutations, retries, pagination, SSR and Suspense integration, and request-ordering guarantees beyond the latest url. It produces render-then-fetch waterfalls. TanStack Query (or router loaders/RSC) solves all of that.

17Explain stale-while-revalidate and query invalidation in TanStack Query.Data

A query's data becomes stale after staleTime (0 by default). Stale data is still served instantly from the cache, and a background refetch fires on mount, window focus, reconnect or invalidation. isFetching is true while the old data stays on screen. After a mutation, invalidateQueries({ queryKey }) marks matching keys (prefix match) stale and refetches the active ones. That's how you keep views consistent without a normalised store.

18How does Suspense change data loading, and what are its pitfalls?Data

Components declare what they need and suspend until it's ready. The nearest <Suspense> shows a fallback, and error boundaries handle failures, so loading and error UI move to wherever you want them in the tree, and components get non-nullable data. Pitfalls: sequential suspenses cause waterfalls (prefetch in loaders, or use parallel queries), promises must be cached and not created during render, fallbacks can flash (use transitions for updates), and you need error boundaries with reset (QueryErrorResetBoundary).

19Where should filter, sort and pagination state live, and why?Routing

In the URL search params, which become the single source of truth. That makes them shareable, bookmarkable and reload-safe, Back/Forward works, they're server-renderable, and loaders can read them before render, so there's no flash. Read with useSearchParams and validate (the URL is user input), and write through navigation. Avoid copying them into useState.

20Compare React Router loaders with Ember route model hooks.Routing

Both fetch before the route renders and feed the component, and both support redirects and error substates. Loaders for all matched routes run in parallel, while Ember resolves parent models first. There are no controllers: query params are plain URLSearchParams. There are no default loading substates (the old UI stays, with useNavigation() for pending). Errors bubble to the nearest errorElement. Loaders re-run after actions or on navigation, and they pair well with a query cache for client-side caching.

21What are transitions, and when would you use one?Concurrent

Updates marked as non-urgent (startTransition/useTransition) that React can interrupt for urgent input, and during which visible content isn't replaced by Suspense fallbacks. Use them for tab switches, navigations, filtering large lists, or any update that triggers heavy rendering or suspends, so the current UI stays interactive with an isPending hint. In React 19 they can be async (Actions).

22How do Actions, useActionState and useOptimistic fit together?Concurrent

An Action is an async function run inside a transition (a form action or startTransition(async…)). useActionState wraps it, exposing the last result as state plus isPending, and queueing submissions. useFormStatus exposes pending to children of the form. useOptimistic shows a temporary value while the Action is pending, which disappears when it settles, giving automatic rollback on failure. Together they replace manual loading, error and optimistic plumbing, and they work with Server Functions.

23Explain the server/client boundary in React Server Components.Server

Server components run only on the server, can be async and access server resources, and ship no JS. 'use client' marks the module where the client graph starts. Those components (and everything they import) are bundled for the browser, still SSR'd, then hydrated. Props crossing the boundary must be serialisable. Functions can't cross, except Server Function references. Server components can be passed into client components as children. You design the boundary to keep heavy, non-interactive code on the server and push interactivity to the leaves.

24How would you protect a Server Function?Server

Treat it as a public HTTP endpoint, because it is one. Authenticate the session inside the function and authorise per resource. Validate and parse every argument with a schema (FormData is untrusted). Avoid leaking internals in errors. Rate-limit where needed. Don't rely on the UI hiding the button. Remember that closure-captured values are sent to the client (encrypted in Next.js) and come back, so don't capture secrets.

25How do you test a React app, and how is that different from Ember?Testing

Testing Library and userEvent at the component level, querying by role and label. Network-level mocking with MSW. Fresh providers per test (QueryClient, memory router). Async assertions with findBy/waitFor. Plus a thin layer of Playwright end-to-end tests. Unlike Ember there's no global settled() (you wait for the expected outcome), no container or owner (you compose providers), and component, integration and acceptance tests blur together because rendering a route tree is just rendering components.

26A test passes locally but fails on CI one time in twenty. How do you approach it?Testing

Reproduce under stress (--repeat, CPU throttling, --sequence.shuffle). Look for un-awaited userEvent or findBy calls, fixed sleeps, shared state between tests (a module singleton, a reused QueryClient, unrestored fake timers or mocks, leaking listeners), dependence on wall-clock time or timezones, and assertions that race background refetches. Replace sleeps with outcome-based waits, isolate state per test, and make time and data deterministic.

27Compound components vs a config-object API: trade-offs?Patterns

Config (<Tabs items=[…]>) is concise, easy to validate and type, and rigid: every customisation becomes a new prop. Compound components (<Tabs><Tabs.Tab/>…) give callers control over markup, ordering and wrappers with less prop bloat, but they need context plumbing, are looser about invalid structures, and are harder to iterate over (you can't easily inspect children). Libraries often offer both: compound primitives with a convenience config wrapper.

28What does <Activity> give you over conditional rendering?Patterns

Hidden-but-mounted UI: state and DOM preserved (form drafts, scroll), effects torn down while hidden and restored when visible, and low-priority pre-rendering of hidden content (the next tab can render before you click it). Conditional rendering destroys and recreates. Costs: memory for hidden trees, and the need for effects that clean up properly (Strict Mode already checks that).

29How would you migrate an Ember app to React incrementally?Migration

Strangler pattern, by route or by leaf. 1) Stand up a React build next to Ember with shared design tokens and an API client. 2) Mount React "islands" inside Ember: a component or modifier that calls createRoot(element).render(<Widget {...args}/>) and unmounts in willDestroy, passing args as props and callbacks for actions. 3) Bridge state: start with server data through a shared TanStack Query client or the same REST/GraphQL API (not ember-data). Bridge auth and session explicitly. 4) Migrate whole routes at a time once leaves are done, ideally behind a top-level router that delegates unknown routes to Ember (or a reverse proxy splitting by path). 5) Port tests with the features, using Testing Library for components and Playwright across both. Avoid a big-bang rewrite, avoid two-way state sync between the frameworks, and keep a running list of what's left.

30Which Ember instincts are most dangerous in React?Migration

1) Mutating state and expecting the UI to follow (@tracked habit). 2) Expecting fine-grained updates and being surprised that children re-render, then over- or under-memoizing. 3) Treating useEffect like didInsert/observers and syncing state with state. 4) Expecting a DI container: services become context, which isn't a store and re-renders every consumer. 5) Reading a value right after setting it (state is a snapshot). 6) Waiting for settled() in tests instead of for outcomes. 7) Assuming the framework owns data (ember-data), when React leaves server state to a library.
