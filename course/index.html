Week 1 · Core mental model · Day 1

JSX, components, rendering

There is no autotracking: a component is a function that React calls again whenever anything upstream might have changed.

  1. 1Concepts15 min
  2. 2Hands-on35 min
  3. 3Check yourself10 min

Concepts

Components are functions, re-run on every render

🔴 New mental model

In Glimmer, reading a @tracked field during render registers a dependency, so only the parts that read it update. React tracks nothing. Instead, when state changes, React calls your component function again, top to bottom, along with every child it renders unless they opt out. It then diffs the new element tree against the previous one and commits the minimal DOM changes.

So UI = f(props, state), and a render is a function call plus a diff rather than DOM work. Because your function will run many times, keep it pure: no side effects, no mutation, and the same output for the same inputs.

A component re-renders when its state changes, its parent re-renders or a context it reads changes. New props aren't a separate trigger, because they only arrive when the parent renders.

JSX is JavaScript, not a template language

🟡 Same goal, different mechanics

JSX compiles to jsx(type, props) calls, so anything that works in an expression works in {}. Attribute names follow the DOM properties, which is why you write className and htmlFor. There are no block helpers:

  • {{#if}} → cond && <X/>, a ternary, or an early return
  • {{#each}} → array.map(item => <Li key={item.id} …/>)
  • {{else}} → the other branch of the ternary
  • {{!-- --}} → {/* */}

What you lose is Glimmer's compile-time knowledge of which parts are static, and the React Compiler (Day 6) exists partly to win that back.

The 0 && trap

🔴 New mental model

a && b evaluates to a when a is falsy. React renders nothing for false, null and undefined, but it renders numbers, including 0, so {labels.length && <Labels/>} prints a literal 0 when the list is empty.

This one bites Ember developers in particular, because {{#if}} treats 0 as falsy and renders nothing. Always give && a boolean (labels.length > 0 &&, !!count &&) or use a ternary.

Plain functions replace helpers

🟢 Direct translation

There's no helper registry and no resolver: a helper is just a function you import. Hoist expensive setup, like an Intl.DateTimeFormat, to module scope so it isn't rebuilt on every render.

Fragments

🟢 Direct translation

Glimmer templates can have several top-level nodes, so you've never needed this. A React component returns one node, so to return siblings without a wrapper <div> you use <>…</>, or <Fragment key={id}> when the fragment needs a key in a list.

  1. Question 1 of 5

    What triggers a re-render?

    Three things: the component's own state changes (a useState/useReducer setter called with a new value), its parent re-renders, or a context it consumes changes. "Props changed" isn't a separate trigger, because props only change when the parent renders, and a child re-renders with its parent whether or not its props changed, unless it's wrapped in memo.

  2. Question 2 of 5

    What is the difference between render and commit?

    Render is React calling your components to get a new element tree and diffing it against the previous one. It's pure, has no DOM access and, in concurrent mode, can be interrupted, restarted or thrown away. Commit applies the diff to the DOM, runs layout effects and then, usually after paint, passive effects. Because a render may never be committed, side effects belong in event handlers or effects, never in render.

  3. Question 3 of 5

    Why className and not class?

    JSX attribute names follow DOM properties, not HTML attributes: className because the property is element.className (class was a reserved word in early JS), and htmlFor because of label.htmlFor. React still writes most of them to the DOM as attributes. For custom elements, React 19 sets a prop as a property when the element defines one, and as an attribute otherwise.

  4. Question 4 of 5

    How do JSX and Glimmer templates differ in what the compiler knows?

    Glimmer templates are a restricted language, so at build time the compiler knows which parts are static and emits opcodes that update only the dynamic bits, driven by autotracking. JSX, by contrast, is arbitrary JavaScript. To the compiler jsx('div', props) is an opaque function call, which is why React has to re-run the component and diff at runtime. The React Compiler closes that gap: assuming your components follow the rules of React, it analyses them and auto-memoizes values and JSX.

  5. Question 5 of 5

    What does {0 && <X/>} render?

    The text "0". && returns its left operand when that operand is falsy, and React renders numbers (including 0 and NaN) but skips false, null, undefined and true. Fix it with a real boolean: {count > 0 && <X/>}.

Week 1 · Core mental model · Day 2

Props, children, composition, lists & keys

Args become props and blocks become children, but keys are where Ember instincts quietly fail.

  1. 1Concepts15 min
  2. 2Hands-on35 min
  3. 3Check yourself10 min

Concepts

Args → props

🟢 Direct translation

Props are the one argument to your function, so destructure them in the signature and give defaults there. There's no this.args proxy, no @ sigil and no distinction between "args" and HTML attributes: everything is a prop, and {...rest} takes the place of ...attributes.

{{yield}} → children

🟢 Direct translation

Whatever you nest inside a component arrives as props.children, typed ReactNode, and you render it wherever the yield would go.

Named blocks → ReactNode props

🟡 Same goal, different mechanics

There's no named-block syntax, because a "slot" is just a prop whose value is JSX. That's more flexible than a named block, since you can compute it, pass it down or default it, and (has-block "footer") becomes a plain truthiness check.

Block params → render props

🟡 Same goal, different mechanics

{{yield issue index}} hands data back to the caller's block. The React equivalent is a function prop that returns JSX: the child calls it with data, and the caller decides the markup. Hooks now cover reusable logic, so render props survive mainly where the data comes from the child's render, such as list items or virtualised rows.

Keys are identity, not a performance hint

🔴 New mental model

React matches old and new children by type + key, and when the key matches it reuses the component instance, along with its state, refs and DOM nodes. So with key={index}, reordering a list keeps instance #0 at position 0 and hands it different data, leaving any local state (a typed input, an open dropdown, a focused element) next to the wrong item.

Use a stable id from the data instead. The flip side is useful too: changing a component's key on purpose is how you reset its state, because React unmounts it and mounts a fresh one.

Props are read-only; composition over configuration

🟡 Same goal, different mechanics

Data flows down and changes flow up through callback props, which is DDAU, just enforced harder. In development React freezes the props object, so assigning to a prop throws in strict-mode code (which every ES module is). Nested objects aren't frozen, so mutating props.issue.title slips through, but it's just as wrong.

Prefer composition to configuration: rather than <Card showHeader headerTitle headerIcon …>, accept header={<CardHeader …/>} or children. It's also the first fix for prop drilling, before you reach for context.

  1. Question 1 of 4

    Why not use the array index as a key?

    A key is how React decides which component instance, with its state and DOM, lines up with which item between renders. With index keys, inserting, removing or reordering items shifts the data under the existing instances, so state, focus, uncontrolled input values and animations stay at the old positions. Index keys are only safe for static lists that never reorder and whose items have no state.

  2. Question 2 of 4

    How do you reset a component's state?

    Change its key. A different key means a different identity, so React unmounts the old instance and mounts a fresh one with initial state. That makes <ProfileForm key={userId} /> the idiomatic way to reset a form when the entity changes, and far better than an effect that resets each field.

  3. Question 3 of 4

    Render props vs children vs hooks: when would you use each?

    Use children or ReactNode props when the parent just decides what goes in a slot. Use a render prop when the child owns data that the caller should turn into markup, such as list items, virtualised rows or a headless select's options. Use a hook when you want to reuse stateful logic with no opinion about markup. Hooks replaced most render props and HOCs for sharing logic, which leaves render props for per-item rendering.

  4. Question 4 of 4

    What is prop drilling, and what fixes it?

    It's passing a prop through intermediate components that don't use it, just to reach a deep child. The first fix is composition: pass the deep child down as children or an element prop, so the layers in between never see the data. Next comes context for genuinely tree-wide values (theme, current user, a store), and then an external store with selectors. Don't reach for context just to save typing.

Week 1 · Core mental model · Day 3

State: useState, immutability, derived state

Mutation is invisible to React: state is a snapshot, setters schedule a new render, and derived values belong in render.

  1. 1Concepts15 min
  2. 2Hands-on35 min
  3. 3Check yourself10 min

Concepts

@tracked mutation → immutable replacement

🔴 New mental model

Autotracking notices this.issue.status = 'done' because the setter is instrumented. React instruments nothing: it compares the new state with the old using Object.is, and a mutated object is the same reference, so React sees no change and nothing re-renders. Worse, other code holding that object now sees a change that was never rendered.

So instead of mutating, you replace: a new array, a new object for the item that changed, and the same references for everything else, which is what later lets memo skip work.

State is a snapshot per render

🔴 New mental model

count is a const captured by the closure of this render, so setCount(count + 1) can't change it. The setter schedules a re-render instead, and only in that next render, when your function runs again, does useState return the new value. That's why logging right after the setter prints the old value, the single most common "React is broken" moment for people coming from mutable models.

Batching

🟡 Same goal, different mechanics

React batches every state update made in the same tick, whether in an event handler, a timeout or a promise, into one re-render, so ten setter calls produce one render. Ember coalesces through the runloop too, but there you can read the new value straight away, whereas here you can't (see the previous section). flushSync forces a synchronous commit, though you'll rarely need it.

Updater functions

🟢 Direct translation

When the next state depends on the previous one, pass a function: setCount(c => c + 1). React queues the updaters and runs them in order against the latest state, so calling it twice adds 2. Calling setCount(count + 1) twice adds only 1, because both calls read the same snapshot.

Derived state = compute during render

🟢 Direct translation

A filtered list, a count or a "Showing X of Y" are getters, not state, so compute them in the component body. Mirroring props or other state into useState + useEffect costs an extra render and a frame of stale UI, and it's a sync bug waiting to happen. Reach for useMemo only when the computation is measurably expensive.

Lazy initial state

🟡 Same goal, different mechanics

useState(expensive()) calls expensive() on every render and throws the result away after the first. Pass the function instead, useState(() => expensive()), and React calls it only once, on mount. The same idea explains the initial… naming convention for props (initialIssues): it signals "read once, then owned locally".

  1. Question 1 of 6

    Why must React state be treated as immutable?

    Because React detects changes by reference (Object.is), and a mutated object keeps its reference, so React bails out and the UI doesn't update. Immutability also keeps each render a consistent snapshot, which concurrent rendering needs because a render can be paused or discarded. It makes memo and useMemo comparisons cheap and correct, too, and lets features like transitions and undo keep older versions around.

  2. Question 2 of 6

    What does console.log(count) print right after setCount(count + 1)?

    The old value. count is a constant captured by this render's closure, and the setter only schedules a new render, so the new value appears when your component function runs again. If you need it straight away, compute it into a local first: const next = count + 1; setCount(next); use(next).

  3. Question 3 of 6

    What is batching?

    React groups all the state updates triggered in the same tick into a single re-render and commit, so several setters still produce one render. Since React 18 this covers timeouts, promises and native handlers as well as React events. You can opt out with flushSync, though that's rarely needed, for example before measuring the DOM.

  4. Question 4 of 6

    When should you use an updater function?

    Whenever the next state is computed from the previous one: counters, toggles and appending to arrays. It matters most when several updates might be queued in one tick, or when the setter runs inside a stale closure such as a timer or subscription, because set(prev => …) always operates on the latest queued value.

  5. Question 5 of 6

    Derived state vs useEffect + setState?

    Derive it. An effect that sets state from props or other state causes a second render, so the first one shows stale data, and it can drift out of sync and is harder to follow. Compute the value in render, adding useMemo only if it's expensive, and keep effects for syncing with external systems rather than with other React state.

  6. Question 6 of 6

    How is this different from @tracked?

    @tracked gives you fine-grained, mutable reactivity: you mutate a field, Glimmer knows exactly which template bits read it, and the new value is readable straight away. React state is coarse and immutable: you replace values, the whole component re-renders and diffs, and the new value only appears in the next render's snapshot. The precision moves from the framework to you, through memoization and where you place state.

Week 1 · Core mental model · Day 4

Events & forms: controlled vs uncontrolled, refs

An input's value is owned either by React or by the DOM, so choose deliberately.

  1. 1Concepts15 min
  2. 2Hands-on35 min
  3. 3Check yourself10 min

Concepts

{{on "click"}} → onClick

🟡 Same goal, different mechanics

Handlers are camelCase props that take a function, and they receive synthetic events: React attaches one listener per event type at the root container and dispatches through the React tree. The event object is a cross-browser wrapper, unpooled since React 17. One surprise: onChange on inputs fires on every keystroke, like the native input event, not on blur.

preventDefault and real forms

🟢 Direct translation

As in Ember, call event.preventDefault() in onSubmit to stop the full-page post. Prefer a real <form> with a submit button over a click handler on a div, because it gives you Enter-to-submit, a11y and FormData for free. (On Day 11, <form action={fn}> handles all of this for you.)

Controlled vs uncontrolled inputs

🟡 Same goal, different mechanics

Controlled inputs use value={state} + onChange, so React state is the single source of truth and the component re-renders on every keystroke. Use them for live validation, character counters, dependent fields and formatting as you type.

Uncontrolled inputs take a defaultValue and let the DOM keep the value, which you read on submit with new FormData(form) or through a ref. That's less code and fewer renders, and it suits simple forms and React 19 Actions.

Mixing the two is a bug. value without onChange makes the input read-only, and switching between undefined and a string triggers the "changing an uncontrolled input to be controlled" warning.

useRef for DOM access

🟡 Same goal, different mechanics

useRef returns a mutable box, { current }, that survives renders and doesn't trigger a render when it changes. Pass it as ref={inputRef} and React sets current to the DOM node after commit, ready for you to focus, measure, scroll or reset an uncontrolled input. Don't read refs during render, though: they're unset on the first render and sit outside React's data flow.

Where Ember hands the element to a modifier, React 19 has the closer match of ref callbacks with cleanup: ref={el => { setup(el); return () => teardown(); }}.

Labels and a11y

🟢 Direct translation

Wrap the control in a <label>, or link the two with htmlFor + id, using useId() for unique ids rather than Math.random(). Screen readers and Testing Library's getByLabelText both depend on it. Put errors in an element with role="alert" so they're announced.

  1. Question 1 of 4

    Controlled vs uncontrolled inputs: trade-offs, and when to use each?

    With controlled inputs (value + onChange), React state always mirrors the input, which allows instant validation, derived UI, programmatic resets and input masking, at the cost of a render per keystroke and more code. With uncontrolled inputs (defaultValue, read via FormData or a ref), the DOM owns the value, so they're simpler, render less, and work with progressive enhancement and React 19 form Actions. Use controlled when other UI depends on the value as it changes; otherwise uncontrolled is fine, and often preferable.

  2. Question 2 of 4

    What is a synthetic event?

    It's React's cross-browser wrapper around a native event, with a consistent interface (target, currentTarget, preventDefault, stopPropagation). React delegates, attaching one native listener per event type to the root container and dispatching through the React component tree, which is why events from portals bubble to their React parents. e.nativeEvent gives you the original.

  3. Question 3 of 4

    useRef vs useState?

    Both persist across renders, but they behave differently when they change. Changing state schedules a re-render, and the value is a per-render snapshot, whereas changing a ref (ref.current = x) is a silent mutation: no render, and visible immediately. So use state for anything that affects output, and refs for DOM nodes, timer ids, previous values and other instance-like data that render doesn't read.

  4. Question 4 of 4

    Why avoid reading the DOM (or refs) during render?

    Render must be pure, and it may run without ever committing (in Strict Mode, concurrent rendering or Suspense retries). On the first render the DOM doesn't exist yet, so ref.current is null, and later the DOM reflects the previous commit rather than the one you're computing. Read it after commit instead, in effects, layout effects or event handlers.

Week 1 · Core mental model · Day 5

Effects: synchronising with external systems

useEffect is not didInsert: it keeps something outside React in sync with your props and state, and most code that reaches for it doesn't need it.

  1. 1Concepts15 min
  2. 2Hands-on35 min
  3. 3Check yourself10 min

Concepts

useEffect synchronises with the outside world

🟡 Same goal, different mechanics

An effect says: once this render has committed, make the outside world (a subscription, a timer, a socket, a non-React widget) match these values. When the values change, React tears down the old sync and sets up a new one, so think in terms of starting and stopping synchronisation rather than "on mount" and "on update". If that sounds like a modifier, it is the closest Ember analogue: a function modifier also returns its teardown (class modifiers use registerDestructor), and it also re-runs when its arguments change.

The dependency array

🟡 Same goal, different mechanics

The dependency array lists every reactive value the effect reads: props, state and anything derived from them. It isn't a "run when X changes" knob to tune by hand, which is why the react-hooks/exhaustive-deps lint rule, not intuition, is the source of truth. Omit the array and the effect runs after every render; pass [] and it runs once per mount, which is only correct when it genuinely reads nothing reactive. When a dependency changes too often, such as an inline object or function, fix the value: move it inside the effect, memoize it, or read it through an Effect Event. Never lie in the array.

Cleanup, and the Strict Mode double-invoke

🟡 Same goal, different mechanics

Return a function from the effect and React calls it before the next run and on unmount. Without it, intervals keep ticking, listeners stack up and sockets leak.

To prove that your cleanup really undoes your setup, <StrictMode> deliberately mounts, unmounts and remounts every component in development, so each effect runs setup → cleanup → setup. The check pays off beyond Strict Mode, because <Activity> and Fast Refresh hide and restore components in the same way. So if the double run breaks something, the bug is in your effect, not in Strict Mode.

You might not need an effect

🔴 New mental model

Most effects in real codebases are unnecessary, so before writing one, check whether it's really one of these:

  • Derived data: compute it during render (Day 3). An effect that calls setState costs an extra render and shows stale UI first.
  • Event-driven logic: "when the user clicks Save, POST and show a toast" belongs in the event handler, not in an effect watching saved.
  • Resetting state when a prop changes: give the component a key.
  • Fetching data: use a data layer (Query, a router loader or RSC), which Day 9 covers.

The test is simple: is this synchronising with something outside React? If not, it isn't an effect.

Race conditions: ignore stale responses

🟡 Same goal, different mechanics

Fetch in an effect, change issueId quickly, and the responses can arrive out of order, so the slow, stale one lands last and wins. ember-concurrency's restartable cancelled the previous run for you, whereas in React the previous run's cleanup is your cancellation point. Give each run a flag that its cleanup flips, or an AbortController that its cleanup aborts. That bookkeeping is also why you'll use a data library for real fetching.

useEffectEvent: read the latest values without re-syncing

🟡 Same goal, different mechanics

Sometimes an effect needs to read a value it shouldn't react to. Take a subscription that calls onNotify unless muted: putting both in the deps resubscribes on every toggle and on every parent render (an inline callback is new each time), but leaving them out makes the closure stale.

useEffectEvent (stable since React 19.2) resolves the dilemma. It wraps a function that always sees the latest props and state and doesn't belong in the deps, provided you call it only from inside effects.

  1. Question 1 of 7

    When do effects run?

    After the render is committed, and usually after the browser has painted, although effects triggered by a discrete input such as a click are flushed before paint. (useLayoutEffect always runs before paint.) On mount the setup runs. On a later render where a dependency changed, compared with Object.is, the previous cleanup runs and then the new setup, and on unmount the cleanup runs one last time. Effects never run during server rendering.

  2. Question 2 of 7

    What is the dependency array really for?

    It tells React which reactive values the effect's synchronisation depends on, so React can skip re-syncing when none of them changed. That's why it must include every prop, state or derived value the effect reads, and why the lint rule enforces it: the array describes the effect rather than scheduling it. If you're tempted to leave something out, restructure instead: move it inside the effect, memoize it, or read it through useEffectEvent.

  3. Question 3 of 7

    Why does Strict Mode run effects twice in development?

    To surface missing or incorrect cleanup. Because it mounts, unmounts and remounts each component, every effect goes setup → cleanup → setup. A correct effect behaves exactly as if it ran once, whereas a leaky one, with a double subscription, an uncleared timer or an unguarded duplicate request, shows up immediately. None of this happens in production.

  4. Question 4 of 7

    How do you handle race conditions when fetching in an effect?

    Give each effect run a way to know it has gone stale. Either declare let ignore = false, set it to true in cleanup and check it before setState, or create an AbortController and abort it in cleanup, which also cancels the network request. Better still, use a library such as TanStack Query or router loaders, which keys requests and handles ordering, caching and dedupe for you.

  5. Question 5 of 7

    Name three cases where you don't need an effect.

    First, derived values: compute them during render, with useMemo if they're expensive. Second, responding to user events: do the work in the event handler. Third, resetting state when a prop changes: use a key. Notifying a parent, chaining state updates and initialising app-wide singletons don't need one either: call the callback in the same handler, combine the updates, or use module scope.

  6. Question 6 of 7

    What does useEffectEvent solve?

    It lets an effect read the latest props or state without making them dependencies, which separates what you synchronise with (the deps) from what you read when something happens (the event). Typical uses are logging with the current user, checking the current muted flag before notifying, or calling the latest onX prop from a subscription. The rules: call it only from effects, never during render, and never pass it to other components.

  7. Question 7 of 7

    How do effects compare to Ember modifiers?

    The lifecycle is the same: both set up against something external and tear down when their arguments change or on destroy. The differences lie in where they live and what drives them. A modifier is bound to an element and used in a template, whereas an effect is bound to a component and declared in its body. Its re-runs follow an explicit deps array rather than autotracking, and it runs after the commit, never during render. The most direct "element modifier" equivalent is a ref callback with cleanup.

Week 2 · Architecture · Day 6

Rendering performance: reconciliation, memoization, React Compiler

Glimmer updates what changed. React re-runs what might have changed, and lets you (or the Compiler) prove it didn't.

  1. 1Concepts15 min
  2. 2Hands-on35 min
  3. 3Check yourself10 min

Concepts

Reconciliation: type + key

🔴 New mental model

Glimmer reuses by template identity, so you rarely think about this. React diffs element trees with two heuristics instead. A different type at the same position (<div> → <span>, ComponentA → ComponentB) unmounts the old subtree and mounts a new one, so its state is lost. The same type and same key keep the instance and update its props.

That makes defining a component inside another component a bug: every render creates a new function, which is a new type, so the child remounts every time. Conditionally wrapping in an extra <div> resets everything below it for the same reason.

Parent renders → children render

🔴 New mental model

When a component renders, every child it returns renders too, recursively, whether or not their props changed. Glimmer never had this cost model, so it's easy to miss.

Usually it doesn't matter, because renders are cheap and React only touches the DOM where the output differs. It starts to matter with big lists, expensive children or high-frequency updates such as typing and dragging.

memo, useMemo, useCallback and referential stability

🔴 New mental model

memo(Component) skips a re-render when every prop is Object.is-equal to last time. That means a single prop that's a fresh object, array or function on each render, such as onSelect={() => …} or style={{…}}, defeats it. So you keep references stable:

  • useCallback(fn, deps) keeps the same function identity until the deps change.
  • useMemo(() => value, deps) does the same for computed values, and caches expensive work too.
  • Primitives are stable for free: pass isSelected={id === selectedId} instead of selectedId, and only the two rows whose boolean flipped re-render.

But memoization isn't free. It costs comparisons and memory, and it makes code noisier, so measure first.

Move state down, lift content up

🟢 Direct translation

Before memoizing, restructure. In Ember, component boundaries are about reuse; in React they also decide what re-renders.

  • Move state down. Put the draft input and its state in a <DraftNote/> component, and typing re-renders only that component.
  • Lift content up. When a stateful wrapper takes children, its parent created those children, so they don't re-render when the wrapper's state changes.

Both fixes cost nothing and keep working when the Compiler arrives.

React Compiler: auto-memoization

🔴 New mental model

Glimmer's compiler already knows what's static and what's dynamic. The React Compiler (v1, stable) closes much of that gap at build time. It's a Babel plugin (an experimental Rust port also exists) that analyses each component and hook and caches JSX subtrees, derived values and callbacks, keyed on their real inputs. In effect it's memo/useMemo/useCallback everywhere, done correctly.

The catch is that it relies on the Rules of React: components are pure, props and state are never mutated, and hooks run unconditionally at the top level. Code that breaks the rules is skipped.

So manual memo still matters: for code the compiler skips, for values handed to non-React libraries that compare identity, for effect dependencies you want explicit, and on codebases that haven't adopted it. This day's stretch goal turns it on.

Finding slow renders: the Profiler

🟡 Same goal, different mechanics

Measure before memoizing, because the slow thing is usually one component, not "React". The React DevTools Profiler is the Ember Inspector's render tab: record an interaction and it shows which components rendered, why ("props changed: onSelect") and how long each took. "Highlight updates when components render" makes the same thing visible live. In code, <Profiler id onRender> reports commit timings, which is how the Day 5 and Day 6 tests count renders.

Week 2 · Architecture · Day 7

State architecture: Context, reducers, external stores

There is no container. "Services" are values placed in the tree, and a context is a transport, not a store.

  1. 1Concepts15 min
  2. 2Hands-on35 min
  3. 3Check yourself10 min

Concepts

Services → Context + a provider

🟡 Same goal, different mechanics

An Ember service is a lazily created singleton from the DI container, available anywhere with @service. React has no container. Instead, createContext defines a slot, a provider puts a value into the tree, and useContext (or use(Context)) reads the nearest provider above. Scope therefore comes from where you render the provider: two providers give two independent "services", which is great for tests and for embedding.

Context is dependency injection, not state management. It carries whatever you put in it, whether that's a reducer's state, a store or a client. In React 19 the context itself is the provider (<MyContext value={…}>), so .Provider is no longer needed.

Every consumer re-renders when the value changes

🔴 New mental model

Ember consumers update only where they read the tracked field that changed. Context has no selector, so when a provider's value changes (by Object.is), every component that reads it re-renders, even if it uses one field and even inside memo. Two habits follow:

  • Memoize the value object. value={{ issues, dispatch }} is a new object on every provider render, so every consumer re-renders every time.
  • Split contexts by update frequency: the stable dispatch in one, the changing issues in another, the theme in a third. Alternatively, put a store in context and subscribe with selectors.

useReducer

🟢 Direct translation

Where a service spreads its updates across @action methods, useReducer(reducer, initial) gathers them into one pure (state, action) => newState function, as Redux does. That function is testable without React and centralises every transition, and dispatch keeps a stable identity, which suits context.

Reach for it when the next state depends on the previous one in several ways, or when updates are naturally named events (added, statusChanged). Type the actions as a discriminated union for exhaustiveness, and throw on unknown ones.

External stores with useSyncExternalStore

🟡 Same goal, different mechanics

A service with @tracked fields is already an external store with fine-grained subscriptions. React's equivalent is to keep widely shared, often updated state outside React and subscribe with a selector through useSyncExternalStore(subscribe, getSnapshot), so a component re-renders only when its snapshot changes. It also prevents tearing, because React makes sure every component in a concurrent render sees the same version of the store. This is the primitive under Zustand, Redux (useSelector), Jotai and friends.

The catch is that the snapshot must be stable for unchanged data, so return a slice rather than a fresh object or array on each call.

Where should state live?

🟡 Same goal, different mechanics

Start local and escalate only when you need to:

  • Local useState in the component that uses it.
  • Lifted to the nearest common parent when siblings share it.
  • URL for anything that should survive reload or be shareable: filters, tabs, selection (Day 10).
  • Context for tree-wide, low-frequency values (current user, theme, feature flags) or for injecting a client or store.
  • External store (Zustand, Redux) for high-frequency, app-wide client state with many readers.
  • Server cache (TanStack Query, loaders) for anything that comes from the server, which is usually most of your "state" (Day 9).

Custom hooks

A hook is just a function that calls hooks. That makes it the unit of reuse for stateful logic.

  1. 1Concepts15 min
  2. 2Hands-on35 min
  3. 3Check yourself10 min

Concepts

Hooks are the unit of reusable stateful logic

🟡 Same goal, different mechanics

Ember spreads reusable stateful logic across ember-resources (reactive values with teardown), stateful helpers and services. In React all of that is a custom hook: a function named useX that calls other hooks. It can own state and effects, and return anything from a value to a tuple or an object.

Each call site gets its own state, so nothing is shared unless the hook reads a context or an external store.

The Rules of Hooks, and why

🔴 New mental model

Call hooks only at the top level of a component or custom hook, never in conditions, loops, nested functions or after an early return, and call them only from React functions.

The reason is that tracked fields are named properties, but hooks have no names or keys. React stores hook state in a list on the component instance and matches it up by call order: hook #1 is the first useState, hook #2 the next, and so on. So if a condition skips a hook on one render, every later hook reads the wrong slot. use() is the one exception, and may be called conditionally.

Composing hooks

🟡 Same goal, different mechanics

Hooks compose like functions. useIssueSearch, for example, is useLocalStorage for the persisted query, plus useDebouncedValue for the settled query, plus a derived filter. Keep each hook small and derive rather than store. Anything a consumer might pass to a memo'd child or an effect's deps should keep a stable identity, so wrap it in useCallback.

Testing hooks with renderHook

🟢 Direct translation

renderHook(() => useThing(args), { initialProps, wrapper }) mounts a throwaway component and exposes the hook's return value as result.current. Wrap state changes in act(), change inputs with rerender(newProps), supply providers such as a QueryClient through wrapper, and control debounces and intervals with fake timers. But when a hook only exists to serve one component, test it through that component instead.

Week 2 · Architecture · Day 9

Data fetching: TanStack Query, Suspense, error boundaries

Server state is a cache you don't own. Stop putting it in useState.

  1. 1Concepts15 min
  2. 2Hands-on35 min
  3. 3Check yourself10 min

Concepts

Server state ≠ client state

🟡 Same goal, different mechanics

Client state, such as UI toggles and form drafts, is synchronous, owned by you and always current. Server state is remote, asynchronous, shared and possibly stale the moment it arrives, so it needs caching, dedupe, background refetch, invalidation after writes, retries and pagination. Ember gave you a store for that. In React, hand-rolling it with useEffect + useState is how codebases accumulate the race conditions from Day 5, so use a server cache instead: TanStack Query, router loaders or RSC.

The query cache vs the ember-data store

🟡 Same goal, different mechanics

Where ember-data keeps one record per type + id, TanStack Query caches by query key, with no normalisation and no identity map. So ['issues','list',{status:'todo'}] and ['issues','detail','1'] are separate entries that both contain issue 1, and you keep them consistent yourself: invalidate related keys after a mutation, or write to them with setQueryData.

A few defaults are worth knowing:

  • staleTime: 0 makes data stale immediately, so remounting, refocusing or reconnecting refetches in the background while the cached data shows. That's stale-while-revalidate.
  • gcTime: 5 min clears unused entries, failed queries retry 3 times, and identical in-flight requests are deduped.
  • ember-concurrency's isRunning and last.error map to isPending, isFetching, isError and error.

Query-key factories

🟢 Direct translation

Keys are arrays compared structurally and hierarchically, so invalidating ['issues'] hits every key that starts with it. Centralise them in a factory so components never hand-write one. And include every input of the queryFn in the key, whether filters, ids or page, because an input that isn't in the key makes different requests share one cache entry.

Mutations and invalidation

🟡 Same goal, different mechanics

An ember-data save() updates the record everywhere. A query cache can't do that, so after a write you tell it what changed. useMutation({ mutationFn, onSuccess }) gives you mutate/mutateAsync, isPending and error, and on success you invalidate the affected keys: active queries refetch and inactive ones are marked stale. Returning the invalidation promise from onSuccess keeps the mutation pending until the fresh data has arrived.

For instant UI, update optimistically instead: onMutate writes the cache, onError rolls back and onSettled invalidates.

Suspense for data

🔴 New mental model

Ember gives each route a loading substate. Suspense generalises that to any component: one that isn't ready suspends by throwing a promise (or calling use(promise)), and the nearest <Suspense fallback> above it shows the fallback until the promise settles. useSuspenseQuery does this for you, which means data is always defined. Loading UI therefore moves out of the component and up the tree, where you choose the granularity. Errors work the same way: thrown, then caught by the nearest error boundary.

There are two catches. Sibling suspending queries inside one component run in series, a waterfall, so hoist or prefetch them. And promises passed to use() must be cached rather than created during render.

Error boundaries are still class components

🔴 New mental model

Ember's per-route error substate becomes an error boundary, and there's still no hook for catching render errors. So a boundary is a class: static getDerivedStateFromError switches to the fallback, and an optional componentDidCatch reports the error.

A boundary catches errors thrown during the render, lifecycle and effects of its subtree. It does not catch errors in event handlers or in async code outside rendering, which you handle yourself. Most apps use the react-error-boundary package, and with Query you wrap it in QueryErrorResetBoundary so "Try again" clears the cached error and refetches.

  1. Question 1 of 7

    Server state vs client state?

    The difference is ownership. Client state belongs to the UI, so it's synchronous, private and always correct: open menus, drafts, selection. Server state belongs to the server, so it's async, shared and stale once fetched, which is why it needs caching, background refresh, dedupe, invalidation and retries.     What is stale-while-revalidate?

    It means serving cached data immediately, even if stale, while refetching in the background, then swapping in the fresh result. In TanStack Query data goes stale after staleTime, which defaults to 0. When a stale query is used again, on mount, focus, reconnect or invalidation, it shows the cached data with isFetching: true and refetches. So users get instant UI and eventual freshness.

    How do query keys work?

    A key is a serialisable array that identifies one cache entry. It's hashed deterministically, so object key order doesn't matter, and matched by prefix for invalidation. Every input to the queryFn belongs in the key, so different inputs get different entries. A key factory keeps them consistent and makes hierarchical invalidation easy: ['issues'] hits every list and detail.

  4. Question 4 of 7

    Optimistic update vs invalidation?

    It's a trade between correctness and speed. Invalidation waits for the server to confirm, then marks related keys stale and refetches, so it's always correct but the UI updates after a round trip. An optimistic update writes the cache, or shows useOptimistic state, before the server answers, rolls back on error, and usually invalidates on settle to reconcile. It feels instant, but it needs rollback logic and can briefly show something false. So save it for high-confidence, low-stakes interactions like toggles, likes and reordering.

  5. Question 5 of 7

    How does Suspense work?

    A component that needs unavailable data suspends during render, by throwing a promise (libraries do this for you) or calling use(promise). React stops rendering that subtree, shows the nearest <Suspense> fallback, and retries once the promise resolves. Inside a transition, though, already-visible content isn't swapped for a fallback. On the server, Suspense boundaries are also streaming points.

    Why aren't error boundaries hooks?

    Because catching an error thrown while rendering children needs a component that can render a different tree in the same commit, after a child failed. That relies on class lifecycle methods, getDerivedStateFromError and componentDidCatch, which have no hook equivalent yet. In practice you write one class, or use react-error-boundary, and compose it like any other component.

    How does this compare with ember-data?

    ember-data/WarpDrive is a normalised identity map: one record per type + id, with relationships, so every view shares a single source of truth. That's simpler and protocol-agnostic, but consistency becomes explicit. Router.map → route objects

🟢 Direct translation

The model hook → loader + useLoaderData

A loader({ params, request }) is the model hook: it runs before the route renders, and the component reads its result with useLoaderData<typeof loader>(). Loaders re-run on navigation and after actions, and can redirect() or throw.

Error and loading substates → errorElement and useNavigation()

React 19 Actions & concurrent features

Transitions mark updates as interruptible, and Actions are async transitions with pending, error and optimistic state built in. This is the closest React gets to ember-concurrency.

  1. 1Concepts15 min
  2. 2Hands-on35 min
  3. 3Check yourself10 min

Concepts

Transitions: urgent vs non-urgent updates

🔴 New mental model

Ember renders every change synchronously inside the runloop, whereas React gives each update a priority. Typing, clicking and hovering are urgent, because the UI must respond immediately. Re-rendering a big filtered list or switching tabs can wait.

startTransition(() => setX(…)) marks an update as one that can wait, a transition. React renders it in the background while the current UI stays on screen, interrupts the work if something urgent happens, and won't replace visible content with a Suspense fallback. useTransition() adds an isPending flag.

Actions: <form action>, useActionState, useFormStatus

🔴 New mental model

In React 19 a transition can be async, and an async transition is an Action. Pass an async function to <form action={fn}> and React calls it with the FormData inside a transition, then resets uncontrolled fields when it finishes.

useActionState(action, initial) wraps the action and returns [state, formAction, isPending]. state is whatever the action returned last, a result or an error, and submissions queue in order. Inside the form, useFormStatus() lets any component read pending without prop drilling. Together they replace the useState × 3 + onSubmit + try/finally boilerplate that an ember-concurrency task saved you from.

One gotcha: the reset also happens when your action returns an error, so fields snap back to their defaultValue. If the user should keep what they typed, return the submitted values in the state and use them as defaults. The same Actions run as Server Functions on Day 12.

useOptimistic

🔴 New mental model

In an ember-concurrency task you save the previous value and restore it by hand. useOptimistic needs no snapshot. const [optimistic, addOptimistic] = useOptimistic(actual, reducer?) returns actual, except while a transition is pending, when it returns the optimistic value you set. Once the transition settles, React drops that layer and shows actual again.

So on success, where you've updated actual, nothing visibly changes. On failure you haven't, so the optimistic value just disappears, and rollback comes for free. Call addOptimistic inside startTransition or an Action.

useDeferredValue

🟡 Same goal, different mechanics

const deferred = useDeferredValue(query) returns a value that lags behind during heavy renders. React first re-renders urgently with the old deferred value, so the input stays responsive, then renders the new one in the background and abandons that render if query changes again. Unlike a timeout() debounce there's no fixed delay, which means it's instant on a fast device and adapts on a slow one. But it doesn't reduce network calls, so for requests you still debounce.

ember-concurrency, mapped

🟡 Same goal, different mechanics
  • task.perform() → an Action or startTransition(async …)
  • task.isRunning → isPending (useTransition, useActionState, useFormStatus, Query's isPending)
  • task.last.value / .error → useActionState's state, or the mutation's data / error
  • restartable (cancel the previous one) → effect cleanup or AbortController; Query cancels for you
  • enqueue → useActionState (submissions queue in order)
  • drop → disable the button while pending, or check isPending
  • timeout() debounce → useDeferredValue (render) or a debounced value (network)

<ViewTransition> (stable in 19.3)

🟢 Direct translation

Where Ember reaches for ember-animated, React wraps content in <ViewTransition>. Updates made in a transition, whether startTransition, an Action or a router navigation, then animate through the browser's View Transitions API. The default is a cross-fade, which you customise with CSS (::view-transition-*) or by name for shared-element morphs, and addTransitionType('forward') tags a transition so the CSS can vary per type. Urgent updates don't animate, which is one more reason to make navigations transitions.

Server Components & the Next.js App Router

The biggest model shift in the course. Components can run only on the server, and the boundary between server and client is something you design.

  1. 1Concepts15 min
  2. 2Hands-on35 min
  3. 3Check yourself10 min

Concepts

React Server Components

🔴 New mental model

FastBoot renders your client app in Node, and then the browser downloads and runs all of it again. A Server Component is different: it runs only on the server, at request or build time, and never ships its code to the browser. That's why it can be async and await the database, the filesystem or secrets directly. It's also why it can't use state, effects, refs, browser APIs or event handlers, since it never re-renders on the client. Its output is serialised as the RSC payload and merged into the client tree. In the App Router, components are server components by default.

'use client' marks a boundary, not "client-only"

🔴 New mental model

'use client' at the top of a file says this module, and everything it imports, is part of the client bundle. It marks the entry point where the server tree hands over to interactive code, so you only need it on the boundary file, not on every component below it. Client components still render on the server (SSR) for the initial HTML, then hydrate.

Props crossing the boundary must be serialisable: primitives, plain objects and arrays, Dates, Maps and Sets, promises, JSX and Server Functions. Regular functions and class instances can't cross. Server components can, though, as the children of a client component.

Server Functions ('use server')

🔴 New mental model

In Ember a write is an adapter call plus an API endpoint you also maintain. A Server Function collapses the two: a function in a 'use server' module, or with the directive in its body, gives the client an opaque reference, and calling it makes a POST that runs the function on the server. Pass one to <form action> and the form works before JS loads, which is progressive enhancement, and pair it with useActionState for results and pending state.

But its arguments come from the network, so treat it as a public API endpoint: validate the input and check auth.

Streaming + Suspense

🔴 New mental model

FastBoot waits for every model hook, then sends everything. On the server, by contrast, every <Suspense> boundary is a streaming point. React sends the shell HTML right away with the fallbacks, then streams each boundary's HTML and RSC payload into the same response as its data resolves, so slow data no longer blocks the whole page. Client components inside hydrate selectively, starting with whichever part the user interacts with. In Next.js, loading.tsx is a Suspense boundary around a route segment.

SSR vs RSC vs FastBoot

🟡 Same goal, different mechanics
  • SSR (classic): render the client app to HTML on the server, then ship all of its JS and hydrate. FastBoot is this.
  • RSC: some components exist only on the server, so their code and dependencies never ship and their output arrives as a serialised tree. RSC is orthogonal to SSR, and you usually do both: RSC builds the tree, then SSR turns it into HTML for first paint.
  • The benefit is less JS, direct data access and no client-server waterfalls. The cost is a server runtime, a mental boundary, and a bundler or framework (Next.js, Waku, or React Router's RSC support).

One catch: context doesn't exist on the server. Server components can't call createContext, and only client components can read context. So put providers in a small 'use client' wrapper, and render it from a server layout around server-rendered children.

Where the Next.js App Router fits

🟡 Same goal, different mechanics

The App Router replaces Router.map with file-system routes under app/. layout.tsx is a persistent wrapper, like application.hbs or a parent route, and page.tsx is a route's UI. loading.tsx and error.tsx are the substates, built on Suspense and error boundaries. Pages are server components that receive params and searchParams as Promises (Next 15+), so you write const { status } = await searchParams. Mutations use Server Functions plus revalidatePath / revalidateTag, and the client router caches RSC payloads between navigations.

    RSC vs SSR?

    They solve different problems, so frameworks use both. SSR renders client components to HTML on the server for a fast first paint, then ships all of that code to the browser to hydrate. RSC introduces components that run only on the server, so their code never ships, they can reach server resources directly, and their output is a serialised React tree rather than HTML.   2. Question 2 of 5

    What does 'use client' actually mean?

    It marks a module as a client entry point, the boundary where the server module graph hands over to modules bundled for the browser. That file and everything it imports become client code, which is still SSR'd and then hydrated. So it doesn't mean "skip SSR", and it only belongs at the boundary, not on every interactive component.   3. Question 3 of 5

    Why can't you pass a function from a server component to a client component?

    Because server and client are separate environments with a network between them. Props crossing the boundary are serialised into the RSC payload, and a closure can't be serialised, since it captures server scope and code that never ships. The exception is a Server Function ('use server'), which crosses as a reference ID the client can invoke over the network. So pass data, JSX as children, or server functions, but never plain callbacks.

  4. Question 4 of 5

    How do Server Functions work?

    In client code, the bundler replaces each exported function in a 'use server' module with a reference, an ID plus the endpoint. When the client calls it, or a form submits to it, React serialises the arguments and POSTs them, and the framework runs the real function on the server and serialises the result back. In Next.js that response can also carry an updated RSC payload after revalidatePath. Forms with a Server Function action work before hydration. And because they're public endpoints, you authenticate and validate every call.

  5. Question 5 of 5

    When would you not use RSC?

    When most components would be 'use client' anyway, as in highly interactive, client-state-heavy apps: editors, canvases, offline-first tools, or dashboards behind auth with little need for SEO. Also when you can't or don't want to run a Node server, because you host statically or have an existing non-JS backend, when the team or tooling isn't ready for the boundary model, and for embedded widgets. Testing React well

Same philosophy as @ember/test-helpers: test what the user sees. The difference is that nothing waits for "settled". You wait for the outcome.

  1. 1Concepts15 min
  2. 2Hands-on35 min
  3. 3Check yourself10 min

Concepts

@ember/test-helpers → Testing Library

🟢 Direct translation

Testing Library shares the "test like a user" philosophy of @ember/test-helpers + qunit-dom. render(<Comp/>) mounts into a container attached to document.body, screen.* queries the document, and userEvent drives real event sequences. Assertions such as toBeInTheDocument, toHaveAttribute and toBeVisible come from @testing-library/jest-dom. What's missing is a container or owner to set up, so instead you wrap the component in whatever providers it needs: a QueryClient, a router, a context.

Query priority

🟢 Direct translation

Where Ember tests lean on data-test-* selectors, Testing Library has a preferred order: getByRole (with name) → getByLabelText → getByPlaceholderText → getByText → getByDisplayValue → getByAltText / getByTitle → getByTestId as a last resort. Role queries come first because they check what assistive tech sees: if you can't find an element by role and name, a screen reader user probably can't either.

Each query has three variants. getBy throws if the element is missing, queryBy returns null for asserting absence, and findBy waits asynchronously.

userEvent vs fireEvent

🟢 Direct translation

fireEvent.click(el) dispatches one synthetic DOM event, whereas userEvent.click(el) simulates the whole interaction: pointer events, mousedown, focus change, mouseup, click. It also respects disabled and pointer-events, and user.type fires per-key events, which makes it the closer match to Ember's click and fillIn. Always create const user = userEvent.setup() and await every call. Reach for fireEvent only for events userEvent doesn't model.

findBy / waitFor vs await settled()

🟡 Same goal, different mechanics

Ember's test waiters track the runloop, pending AJAX and timers, so await settled() waits until everything is idle. React has no global settled state, so you wait for the outcome you expect instead. await screen.findByRole(…) retries until the element appears (1 s by default), and await waitFor(() => expect(…)) retries an assertion. act() flushes React's own work, but render, userEvent and RTL's async utilities already wrap it, so don't add your own.

Fake timers are vi.useFakeTimers() + act(() => vi.advanceTimersByTime(ms)). Tell userEvent about them with userEvent.setup({ advanceTimers: vi.advanceTimersByTime }), or its internal delays hang.

Mocking the network: MSW

🟢 Direct translation

Mock at the network boundary, not the module boundary, so your real data layer runs unchanged. Mock Service Worker, the closest thing to Mirage, does this by intercepting fetch in Node and the browser, with per-test handlers through server.use(http.get(…)). This course uses an in-memory fake API instead, which keeps the exercises dependency-free.

Test behaviour, use accessibility as the strategy

🟢 Direct translation

A good test survives a refactor that doesn't change behaviour, and fails when behaviour breaks. So avoid asserting on state values, hook calls, incidental class names, internals or snapshot blobs. Query by role, name and state (selected, expanded, pressed) and drive with the keyboard, and you test accessibility for free. Today's exercise makes this measurable, because your tests are only as good as the bugs they catch.

Patterns, TypeScript & modern APIs

Patterns you already know from Ember, in React's vocabulary, plus the APIs React 19 added.

  1. 1Concepts15 min

Concepts

Compound components via context

🟡 Same goal, different mechanics

Compound components are the React spelling of yielding contextual components with hash. <Accordion><Accordion.Item><Accordion.Trigger/>… gives the caller full control of the markup while the parent owns the state. The parent provides that state through context, and each part reads it, throwing a helpful error outside a parent. Attach the parts with Object.assign(Root, { Item, Trigger, Panel }).

Portals

🟡 Same goal, different mechanics

Like {{#in-element}}, createPortal(jsx, domNode) renders children into another DOM node, usually document.body, so modals, toasts and popovers escape overflow: hidden and stacking contexts.

The surprise is that in the React tree the portal is still a child of the component that rendered it. Context flows into it, and synthetic events bubble to React ancestors, not DOM ancestors. So don't stopPropagation inside a dialog just to stop backdrop clicks; check e.target === e.currentTarget on the backdrop instead. The native <dialog> element with showModal() is also worth considering.

ref is just a prop now

🟢 Direct translation

In React 19, function components receive ref like any other prop, so forwardRef is obsolete: still supported, but slated for deprecation. Type it with ComponentProps<'input'>, which already includes ref, and pass it on to the element. Ref callbacks can also return a cleanup function, which makes a ref callback a complete element modifier.

<Activity>: hide without unmounting

🔴 New mental model

Conditional rendering unmounts, so state, DOM and scroll position are gone. In Ember you'd keep the element and toggle a class, but its modifiers keep running. <Activity mode="hidden"> (stable since 19.2) does better: the subtree stays mounted behind display: none and keeps its state and DOM, while its effects unmount, so subscriptions pause, and updates to it render at the lowest priority. mode="visible" restores it instantly and re-mounts the effects. Use it for tabs, back/forward caches and pre-rendering the likely next screen.

Typing components

🟡 Same goal, different mechanics
  • Extend native props: ComponentProps<'button'> (or ComponentPropsWithoutRef when you omit ref) and Omit<…, 'onChange'> when you change a signature.
  • Generic components: function Select<T>({ items, getLabel, onChange }: SelectProps<T>). TypeScript infers T from usage. In .tsx, arrow generics need <T,>.
  • Discriminated-union props make invalid combinations unrepresentable: { variant: 'link'; href: string } | { variant: 'button'; onClick(): void }.
  • ReactNode for anything renderable, ReactElement only when you must have an element.

Ember needed Glint to type-check templates, whereas JSX is just TypeScript.

Fragment refs and <ViewTransition> (19.3)

🔴 New mental model

Ember reaches a group of elements through a modifier on a wrapper, or querySelectorAll. Fragment refs (stable in 19.3) need no wrapper: <Fragment ref={ref}> gives you a FragmentInstance that addresses all of its first-level DOM children through addEventListener, observeUsing(intersectionObserver), getClientRects() and focus(). That makes visibility tracking and focus management around arbitrary children straightforward. <ViewTransition>, from Day 11, animates transition-driven updates with the View Transitions API.

  1. Question 1 of 5

    What are compound components, and how do you build them?

    They're a set of components that work together under a parent and share implicit state, such as <Tabs><Tabs.List><Tabs.Tab/>…, so the caller composes the markup freely while the parent owns the behaviour. The parent creates a context holding state and actions, each part consumes it through a hook that throws outside the parent, and the parts hang off the parent as static properties. They're the React equivalent of yielding contextual components via hash.

  2. Question 2 of 5

    Why portals, and how do events bubble through them?

    Portals render into a different DOM node, usually body, so modals, tooltips and toasts escape clipping, overflow and z-index stacking. Events, though, bubble through the React tree, not the DOM tree. So a click inside a portal reaches the onClick of the component that rendered it, even though the DOM node lives elsewhere, and context flows through the same way. Native listeners on the DOM ancestors won't see those events.

  3. Question 3 of 5

    What changed with refs in React 19?

    ref became a regular prop for function components, so forwardRef is no longer needed. Ref callbacks can now return a cleanup function that runs on detach, instead of being called with null, and useRef requires an argument. The same release replaced <Context.Provider> with <Context>. Then 19.3 added <Fragment ref>, which exposes a FragmentInstance spanning the fragment's children.

  4. Question 4 of 5

    <Activity> vs conditional rendering?

    Conditional rendering unmounts the hidden branch, destroying its state and DOM and running effect cleanups, so showing it again mounts fresh. <Activity mode="hidden"> instead keeps it mounted behind display: none with its state and DOM intact. Its effects are torn down while hidden and re-run when visible, and its updates render at low priority. So use Activity when returning to a view should be instant and stateful, and conditional rendering when hidden UI should really go away.

  5. Question 5 of 5

    How do you type a generic component?

    Declare the type parameter on the function and use it in the props, as in function List<T>({ items, renderItem }: { items: T[]; renderItem: (t: T) => ReactNode }), and TypeScript infers T at the call site. Constrain it when you need fields (T extends { id: string }). For arrow functions in .tsx, write <T,> so it isn't parsed as JSX. Wrapping in memo or forwardRef used to need a cast, but with ref as a prop in 19, plain generic functions just work.

Final review: 30 questions

Set a timer: about 40 seconds per answer, out loud, before you reveal. Two per concern, plus a few that cut across the whole course.

1Walk me through what happens when setState is called.Rendering

The setter enqueues an update on that component's fiber with a priority, or lane. Inside an event it's batched with other updates, and inside a transition it gets a lower priority. Then React schedules a render, which happens in two phases.

During render, React walks down from the root, re-running the updated component and, by default, its descendants, while memoized subtrees bail out when their props are Object.is-equal. It computes the new state by applying the queued updates in order, reconciles the new elements against the current fiber tree by type and key, and collects DOM mutations. A concurrent render can be interrupted at this point.

During commit, React applies the DOM changes synchronously, attaches refs and runs layout effects. The browser paints, then passive effects (useEffect) run. And if the new state is Object.is-equal to the old, React can bail out before any of this.

2React has no fine-grained reactivity. Why is it still fast enough, and when isn't it?Rendering

Because a re-render is only a JS function call plus a diff of lightweight element objects, and the expensive part, DOM work, happens only where the output changed. On top of that, batching collapses updates, concurrent rendering keeps input responsive during heavy work, and the React Compiler skips unchanged subtrees. It struggles when very large trees re-render on high-frequency updates, such as typing in a big form or dragging, and when render functions are expensive. The fixes are state colocation, memoization, useDeferredValue, virtualisation, or an external store with selectors.

3How do keys affect component identity and state?Components

React matches children between renders by type and key. With the same type and key, the instance is reused along with its state, refs and DOM, whereas a different key means unmount and remount. That's why index keys are risky: they tie state to positions, so reordering moves state onto the wrong items. Stable data ids prevent this, and changing a key on purpose resets a component, as in <Form key={id}/>.

4How would you design a reusable Select that works with any item type?Components

As a generic component, Select<T>, with items: T[], getKey, getLabel, and value / onChange typed by T. Beyond the types, it should be controlled with an optional uncontrolled default, accessible through a listbox or combobox pattern or a native <select>, and compositional, with render props or compound parts for custom options. Native props and ref pass through to the trigger. Ideally I'd build it on a headless library such as React Aria, Radix or Ariakit, so keyboard handling and a11y are already solved.

5How would you structure state in a large app?State

By ownership and lifetime, not by "global vs local". First, server state, usually most of it, goes in a server cache: TanStack Query, loaders or RSC. Second, URL state such as filters, tabs, selection and pagination goes in the router. Third, local UI state stays colocated in components, lifted only as far as needed. Fourth, cross-cutting client state such as the auth session, preferences or a complex editor goes in context when it changes rarely, or in an external store with selectors when it changes often and is widely read. Throughout, derive rather than duplicate, keep one source of truth per fact, use reducers for complex transitions, and put feature boundaries around providers.

6Why is mutating state a bug, even when the UI seems to update?State

Because React decides whether to re-render by reference equality, and a mutated object is still the same reference. So memo, useMemo, effect deps and bail-outs all treat it as unchanged, and the UI only appeared to update because something else triggered a render. Mutation also corrupts the previous render's snapshot, which breaks concurrent rendering, transitions and Strict Mode's double renders, and it makes behaviour depend on timing.

7Controlled or uncontrolled for a 30-field settings form?Events & forms

Mostly uncontrolled, because controlled inputs re-render the form on every keystroke and need a state field each. So use native inputs with defaultValue, read them through FormData in a form Action, and validate on submit or blur with native constraints plus a schema. Make a field controlled only where other UI depends on its live value. For field arrays, dirty tracking and richer validation, a form library such as React Hook Form, which is itself uncontrolled and ref-based, is the next step.

8How do React events differ from native DOM events?Events & forms

They're synthetic wrappers, dispatched by delegation from the root container and propagating through the React component tree, portals included. The handlers are props, and e.nativeEvent gives you the original. A few behaviours differ. onChange fires on every input, unlike the native change event. stopPropagation stops React propagation, but native listeners on ancestors may still see the event, depending on where they're attached. And returning false doesn't prevent the default, so call preventDefault().

9When is useEffect the right tool, and when is it a code smell?Effects

It's right for synchronising with external systems keyed on props or state: subscriptions, timers, non-React widgets, imperative DOM APIs and analytics on visibility. It's a smell when it computes derived state, responds to a user event that belongs in the handler, resets state on a prop change where key would do, fetches without a race guard or cache, or chains state updates. The rule of thumb is that if there's no external system, there's no effect.

10Explain stale closures with an example, and how you avoid them.Effects

Each render's functions capture that render's props and state. So a setInterval(() => setCount(count + 1), 1000) created in an effect with [] deps sees count = 0 forever. There are four ways out. First, an updater function, setCount(c => c + 1). Second, a correct dependency array, so the effect re-subscribes when inputs change. Third, useEffectEvent, which reads the latest values in an effect callback without re-syncing. Fourth, for imperative code, a ref holding the latest value.

11When do you use memo, useMemo and useCallback, and what changes with the React Compiler?Performance

Without the compiler, after measuring, I use memo for expensive components that often re-render with the same props, such as list rows and charts. useCallback and useMemo then keep those components' props stable, cache expensive computations and stabilise effect deps. With the compiler most of this is automatic, so manual memoization comes out. What's left is code the compiler skips because it breaks the rules, identity for third-party libraries, and architectural fixes such as state colocation and virtualisation, which no compiler does for you.

12A list of 5,000 issues stutters when typing in its filter. What do you do?Performance

Profile first, then work through the fixes. First, keep the input responsive by applying the filter to the list through useDeferredValue or startTransition. Second, virtualise the list with TanStack Virtual so only visible rows render. Third, memoize rows with stable props, or let the compiler do it. Fourth, make the filter itself cheap, for example by precomputing lower-cased titles with useMemo. And if the data allows, move filtering to the server with debounced queries.

13Context vs an external store vs TanStack Query: how do you choose?Architecture

By where the data comes from and how often it changes. Query is for anything fetched from a server, because it brings caching, invalidation and background refresh. Context is for injecting dependencies and rarely changing tree-wide values such as the theme, the user or a client instance, since every consumer re-renders on change. An external store with selector subscriptions, like Zustand or Redux on useSyncExternalStore, is for frequently changing client state shared across distant components. They often combine: context provides a store, and components select from it.

14What is tearing, and how does React prevent it?Architecture

Tearing is when one render shows inconsistent versions of the same external data. A concurrent render yielded mid-way, the store changed in between, and so some components read the old value and some the new. useSyncExternalStore prevents it by checking snapshots during render and forcing a synchronous re-render if the store changed. React-managed state, useState and context, can't tear in the first place.

15Why do the Rules of Hooks exist?Hooks

Because React associates hook state with a component by call order, not by name. Calling hooks conditionally, in loops or after early returns changes that order between renders, so state is read from the wrong slot. The rules, top level only and only from components and hooks, keep the order stable. The lint plugin enforces them, and the Compiler relies on them.

16Design a useFetch(url) hook. Then tell me why you wouldn't ship it.Hooks

It holds { data, error, status } in state, with an effect on [url] that resets to loading, fetches with an AbortController or an ignore flag cleaned up on change, and sets state on resolve or reject. I wouldn't ship it because of everything it lacks: caching and dedupe across components, background revalidation, invalidation after mutations, retries, pagination, SSR and Suspense integration, and ordering guarantees beyond the latest url. It also produces render-then-fetch waterfalls. TanStack Query, router loaders or RSC solve all of that.

17Explain stale-while-revalidate and query invalidation in TanStack Query.Data

A query's data becomes stale after staleTime, which is 0 by default. Stale data is still served instantly from the cache, while a background refetch fires on mount, window focus, reconnect or invalidation, and isFetching is true as the old data stays on screen. After a mutation, invalidateQueries({ queryKey }) marks keys matching that prefix stale and refetches the active ones. That's how you keep views consistent without a normalised store.

18How does Suspense change data loading, and what are its pitfalls?Data

Components declare what they need and suspend until it's ready. The nearest <Suspense> shows a fallback and error boundaries handle failures, so loading and error UI move wherever you want them in the tree, and components get non-nullable data. There are four pitfalls. First, sequential suspenses cause waterfalls, so prefetch in loaders or use parallel queries. Second, promises must be cached, not created during render. Third, fallbacks can flash, so make updates transitions. Fourth, you need error boundaries that reset, such as QueryErrorResetBoundary.

19Where should filter, sort and pagination state live, and why?Routing

In the URL search params, as the single source of truth. That makes them shareable, bookmarkable and reload-safe, Back and Forward work, they're server-renderable, and loaders can read them before render, so nothing flashes. Read them with useSearchParams and validate them, because the URL is user input. Write them through navigation, and don't copy them into useState.

20Compare React Router loaders with Ember route model hooks.Routing

Both fetch before the route renders and feed the component, and both support redirects and error substates. The differences start with timing: loaders for all matched routes run in parallel, whereas Ember resolves parent models first. There are no controllers, so query params are plain URLSearchParams. There are no default loading substates either; the old UI stays while useNavigation() reports pending. Errors bubble to the nearest errorElement. And loaders re-run after actions or on navigation, which pairs well with a query cache for client-side caching.

21What are transitions, and when would you use one?Concurrent

They're updates marked as non-urgent with startTransition or useTransition. React can interrupt them for urgent input, and it doesn't replace visible content with Suspense fallbacks while they run. So use them for tab switches, navigations, filtering large lists, or any update that renders heavily or suspends, and the current UI stays interactive with an isPending hint. In React 19 they can also be async, which makes them Actions.

22How do Actions, useActionState and useOptimistic fit together?Concurrent

An Action is an async function run inside a transition, either as a form action or through startTransition(async…). The hooks layer onto it. useActionState wraps the Action, exposing the last result as state plus isPending, and queues submissions. useFormStatus exposes pending to the form's children. useOptimistic shows a temporary value while the Action is pending, which disappears when it settles, so failure rolls back automatically. Together they replace manual loading, error and optimistic plumbing, and they work with Server Functions too.

23Explain the server/client boundary in React Server Components.Server

Server components run only on the server, so they can be async, access server resources and ship no JS. 'use client' marks the module where the client graph starts: it and everything it imports are bundled for the browser, still SSR'd, then hydrated. Props crossing that boundary must be serialisable, so functions can't cross unless they're Server Function references, although server components can be passed into client components as children. You design the boundary to keep heavy, non-interactive code on the server and push interactivity to the leaves.

24How would you protect a Server Function?Server

Treat it as a public HTTP endpoint, because it is one. First, authenticate the session inside the function and authorise per resource, rather than relying on the UI hiding the button. Second, validate and parse every argument with a schema, since FormData is untrusted. Third, don't leak internals in errors, and rate-limit where needed. Finally, remember that closure-captured values travel to the client and back, encrypted in Next.js, so don't capture secrets.

25How do you test a React app, and how is that different from Ember?Testing

Mostly at the component level, with Testing Library and userEvent querying by role and label, MSW mocking the network, fresh providers such as a QueryClient and memory router per test, and async assertions through findBy/waitFor. A thin layer of Playwright end-to-end tests sits on top. Three things differ from Ember. There's no global settled(), so you wait for the expected outcome. There's no container or owner, so you compose providers. And component, integration and acceptance tests blur together, because rendering a route tree is just rendering components.

26A test passes locally but fails on CI one time in twenty. How do you approach it?Testing

First, reproduce it under stress with --repeat, CPU throttling or --sequence.shuffle. Then look for the usual suspects: un-awaited userEvent or findBy calls, fixed sleeps, state shared between tests (a module singleton, a reused QueryClient, unrestored fake timers or mocks, leaking listeners), dependence on wall-clock time or timezones, and assertions that race background refetches. The fix is to replace sleeps with outcome-based waits, isolate state per test, and make time and data deterministic.

27Compound components vs a config-object API: trade-offs?Patterns

It's control against simplicity. A config API (<Tabs items=[…]>) is concise and easy to validate and type, but rigid, because every customisation becomes a new prop. Compound components (<Tabs><Tabs.Tab/>…) give callers control over markup, ordering and wrappers with less prop bloat. In exchange they need context plumbing, are looser about invalid structures, and are harder to iterate over, since you can't easily inspect children. So libraries often offer both: compound primitives with a convenience config wrapper.

28What does <Activity> give you over conditional rendering?Patterns

Hidden-but-mounted UI, whereas conditional rendering destroys and recreates. State and DOM survive, so form drafts and scroll positions do too. Effects are torn down while hidden and restored when visible. And hidden content pre-renders at low priority, so the next tab can render before you click it. The costs are memory for hidden trees and effects that must clean up properly, which Strict Mode already checks.

29How would you migrate an Ember app to React incrementally?Migration

With the strangler pattern, by route or by leaf. First, stand up a React build next to Ember, sharing design tokens and an API client. Second, mount React "islands" inside Ember: a component or modifier calls createRoot(element).render(<Widget {...args}/>), passes args as props and callbacks for actions, and unmounts in willDestroy. Third, bridge state, starting with server data through a shared TanStack Query client or the same REST/GraphQL API rather than ember-data, and bridge auth and session explicitly. Fourth, once the leaves are done, migrate whole routes, ideally behind a top-level router that delegates unknown routes to Ember, or a reverse proxy that splits by path. Fifth, port tests with the features, using Testing Library for components and Playwright across both. Throughout, avoid a big-bang rewrite and two-way state sync between the frameworks, and keep a running list of what's left.

30Which Ember instincts are most dangerous in React?Migration

The worst is mutating state and expecting the UI to follow, which is the @tracked habit. Close behind it:

  • Expecting fine-grained updates, being surprised that children re-render, then over- or under-memoizing.
  • Treating useEffect like didInsert or an observer, and syncing state with state.
  • Expecting a DI container. Services become context, which isn't a store and re-renders every consumer.
  • Reading a value right after setting it, when state is a snapshot.
  • Waiting for settled() in tests instead of for outcomes.
  • Assuming the framework owns data, as ember-data did, when React leaves server state to a library.
